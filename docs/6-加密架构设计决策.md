# 加密架构设计决策

> 基于加密技术选型参考的进一步细化

---

## 决策记录

### 决策一：接受硬件信任假设

**结论**：使用 MiTEE（或兼容 TEE）作为盲服务器计算的基础。

**理由**：
- Standby 目标用户在小米生态，MiTEE 是天然选择
- TEE 性能接近明文计算（vs FHE 的数个数量级差距）
- 硬件隔离比纯软件方案更可信
- 侧信道攻击风险可通过软件防护缓解

**影响**：
- 服务器端计算在 TEE Enclave 内执行
- 数据进入 TEE 前加密，出 TEE 后加密
- TEE 外的任何组件（包括服务器管理员）无法看到明文

---

### 决策二：用户感知延迟最短

**原则**：能端侧做的不做服务端，服务端必须做的用 TEE。

**端侧 vs 服务端计算分配**：

| 计算任务 | 执行位置 | 理由 |
|---------|---------|------|
| 情感分析（自己的表达） | **端侧** | 不需要服务端，减少延迟 |
| 共鸣预检测（本地缓存匹配） | **端侧** | 快速反馈，不需要网络 |
| 心物推荐（本地模型推理） | **端侧** | Rust FFI 端侧推理 |
| 密钥协商 / 消息加密 | **端侧** | Signal 协议天然端侧 |
| 共鸣确认（跨用户匹配） | **服务端 TEE** | 需要聚合多用户数据 |
| 知己检测（关系计算） | **服务端 TEE** | 需要跨用户关系图 |
| 群体共识聚合 | **服务端 TEE** | 需要全局数据 |
| 内容安全检测 | **端侧预筛 + 服务端 TEE 确认** | 端侧过滤明显违规，服务端处理边界情况 |

**延迟预算**：

```
端侧操作: < 50ms（无网络开销）
服务端 TEE: < 200ms（网络 + TEE 计算）
用户感知: 端侧即时，服务端"几乎即时"
```

### 决策三：安全性为最高考虑

**结论**：匿名路由在 MVP 阶段就是必须的，不能推迟。

**影响**：
- 所有通信必须经过匿名路由层
- 服务端不能知道"谁在和谁通信"
- 即使内容加密，元数据也必须保护

**匿名路由方案选择**：

| 方案 | 延迟 | 安全性 | 复杂度 | 适用性 |
|------|------|--------|--------|--------|
| Tor | 高（秒级） | 高 | 低（复用） | 不适合实时通信 |
| Mixnet | 中（百毫秒级） | 高 | 高（自建） | 适合批量消息 |
| Oblivious HTTP | 低 | 中 | 中 | 适合请求去关联 |
| 批量上传 + 随机延迟 | 低 | 中 | 低 | 最简方案 |

**推荐方案**：分层匿名

```
Layer A: 批量上传 + 随机延迟（基础防护）
  - 用户表达不立即发送，批量打包
  - 添加随机延迟（0-30秒）
  - 打乱时间关联性

Layer B: Oblivious HTTP（请求去关联）
  - 请求经过代理，服务器看不到真实 IP
  - 代理不知道请求内容（加密）
  - 服务器不知道请求来源

Layer C: 可选增强（高安全场景）
  - 知己通信使用 mixnet
  - 特殊敏感表达使用 Tor
```

## 细化架构

### 端侧架构（Flutter + Rust FFI）

```
┌─────────────────────────────────────────────────┐
│                   端侧计算层                      │
├─────────────────────────────────────────────────┤
│                                                   │
│  ┌──────────────┐  ┌──────────────┐              │
│  │ Signal 协议栈  │  │ 本地推理引擎  │              │
│  │ (libsignal)   │  │ (Rust FFI)   │              │
│  │               │  │              │              │
│  │ - X3DH        │  │ - 情感分析    │              │
│  │ - Double      │  │ - 共鸣预检测  │              │
│  │   Ratchet     │  │ - 心物推荐    │              │
│  │ - MLS         │  │              │              │
│  └──────────────┘  └──────────────┘              │
│                                                   │
│  ┌──────────────┐  ┌──────────────┐              │
│  │ 本地数据层    │  │ 匿名路由客户端│              │
│  │              │  │              │              │
│  │ - 感受缓存    │  │ - 批量打包    │              │
│  │ - 共鸣索引    │  │ - 随机延迟    │              │
│  │ - 关系图谱    │  │ - OHTTP 代理  │              │
│  │   (本地副本)  │  │              │              │
│  └──────────────┘  └──────────────┘              │
│                                                   │
└─────────────────────────────────────────────────┘
```

### 服务端架构（Gateway + TEE Engine）

```
┌─────────────────────────────────────────────────┐
│                 服务端计算层                       │
├─────────────────────────────────────────────────┤
│                                                   │
│  Gateway (Rust/Axum)                              │
│  ├── 匿名路由层                                   │
│  │   - OHTTP 代理                                 │
│  │   - 请求去关联                                  │
│  │   - 批量调度                                    │
│  │                                               │
│  └── 请求分发                                     │
│       ↓                                           │
│  TEE Engine (MiTEE / OP-TEE)                     │
│  ┌─────────────────────────────────────────────┐ │
│  │  Enclave 内部                                │ │
│  │                                              │ │
│  │  数据解密 → 计算 → 结果加密                    │ │
│  │                                              │ │
│  │  - 共鸣确认（跨用户匹配）                      │ │
│  │  - 知己检测（关系计算）                        │ │
│  │  - 群体共识聚合                               │ │
│  │  - 内容安全确认                               │ │
│  │                                              │ │
│  │  输出: 加密结果 + 差分隐私噪声                 │ │
│  └─────────────────────────────────────────────┘ │
│       ↓                                           │
│  加密结果 → 返回用户                               │
│                                                   │
└─────────────────────────────────────────────────┘
```

### 数据流示例：用户表达 → 共鸣检测 → 知己发现

```
用户 A 写下感受
    │
    ▼
[端侧] 情感分析（本地模型）→ 生成情感向量
    │
    ▼
[端侧] Signal 加密 + 匿名路由批量打包
    │
    ▼
[网络] OHTTP 代理 → Gateway（不知道来源）
    │
    ▼
[TEE] 解密 → 与群体情感向量匹配 → 检测共鸣
    │
    ▼
[TEE] 如果发现共鸣 → 检查是否触发知己关系
    │
    ▼
[TEE] 结果加密 → 返回用户 A
    │
    ▼
[端侧] 解密 → 展示"有 X 人和你感受相同"
    │
    ▼
（如果是知己）→ 展示"有个人总是跟你有同样的感受"
```

## 待解决问题

1. **TEE 远程认证**：用户如何验证服务器确实在 TEE 内执行计算？
   - 需要 TEE attestation 机制
   - 用户端验证 TEE 签名

2. **多设备同步**：无手机号绑定，如何同步密钥？
   - 方案 A：设备间直接配对（蓝牙/NFC）
   - 方案 B：助记词恢复
   - 方案 C：知己互助恢复

3. **群体共识的差分隐私**：输出给供给侧的数据如何加噪？
   - 需要设计隐私预算（ε）
   - 平衡数据可用性和隐私保护
