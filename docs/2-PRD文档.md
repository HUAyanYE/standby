## 一、产品定位

### 1.1 一句话定位

**别的产品是「人→内容→人」，Standby 是「人→事物→感受→人」。中间多了一个「事物」——心物，一切都不一样了。**

### 1.2 与现有产品的功能级对比

| 维度 | 微博/小红书 | 微信朋友圈 | Soul/陌陌 | 日记 App | **Standby** |
|---|---|---|---|---|---|
| 驱动力 | "我想让别人看到我" | "我的熟人在看" | "我想认识人" | "我想记录自己" | **"这个事物让我有话想说"** |
| 内容逻辑 | 流量驱动 | 关系链驱动 | 匹配驱动 | 纯私人 | **共鸣驱动** |
| 关系建立 | 先关注人→看内容 | 已有关系 | 算法匹配 | 无社交 | **先共享体验→发现人** |
| AI 角色 | 推荐算法 | 无 | 匹配算法 | 无 | **五引擎协同** |
| 真实性 | 低（流量表演） | 中（熟人表演） | 低（匿名随意） | 高（纯私人） | **高（匿名但真诚）** |
| 身份机制 | 半实名 | 强实名 | 匿名 | 无 | **强实名注册+全匿名展示** |
| 反应机制 | 点赞/评论 | 点赞/评论 | 点赞/匹配 | 无 | **五态反应（共鸣/无感/反对/未体验/有害）** |
| 内容结构 | 独立帖子+评论 | 朋友圈+评论 | 动态+聊天 | 私人日记 | **心物+感受链（单层，每条感受形成独立心物）** |
| 关系模型 | 关注/粉丝 | 好友 | 匹配/关注 | 无 | **共鸣→知己（自然涌现）** |

## 二、核心概念的功能定义

### 2.1 心物模型（Seedstone Model）

心物是一切交互的起点。关于心物的产品哲学参见《产品理念说明书》第四章。

#### 心物类型

| 类型 | 示例 | 感受的来源 |
|---|---|---|
| 文字 | 书中的某段话、一篇深度报道 | "这句话击中了我" |
| 图片 | 一张街景照片、一幅画 | "这个画面让我想起……" |
| 视频 | 一段纪录片片段、一场演讲 | "这个人说的话我深有感触" |
| 声音 | 一首歌、一段环境音、一次口述 | "听到这个声音我就回到了那个瞬间" |
| 物件 | 一个杯子、一张旧车票 | "这个东西承载了一段记忆" |
| 场所 | 某个咖啡馆、某条街道 | "在这里我经历过……" |

#### 心物来源（三种）

| 来源 | 形成方式 | 特点 |
|---|---|---|
| **平台初始心物** | 编辑团队/AI 筛选高质量内容 | 冷启动用，保证基础质量 |
| **用户内容直接成为心物** | 用户发布的感受/经历被系统识别为有心物价值 | 原生、真实、多元 |
| **AI 整理心物素材** | AI 从多种来源提取、整理符合心物标准的客观素材，供用户选择使用 | 降低用户准备成本，用户只需关注情感表达 |

#### 冷启动策略

新用户首次使用时，平台上可能还没有用户自产的心物和感受链。冷启动依赖三个来源：

1. **运营团队填充心物**：内测期间，运营团队负责准备高质量的初始心物，保证新用户有内容可浏览
2. **内测用户内容**：内测用户发布的内容可作为触发新用户表达的素材
3. **AI 引导表达**：AI 向用户推荐可能引发感受的客观素材，激发表达欲望——用户只需关注"我有什么感受"，不需要自己去找心物

**冷启动体验原则**：
- 新用户看到的是平台初始心物，不是空白页面
- 心物下方的感受链可能为空（显示"还没有人留下感受，写下你的感受..."）
- AI 不引导情感方向，只提供客观素材

#### 心物内容标准

- **完整性**：需要有充足的信息量和上下文，不是碎片化的标题
- **具体性**：有细节、有前因后果、有引发思考的空间
- **真实性**：基于真实存在的事物、事件、作品
- **有形性**：必须是可被体验的、具体的、可感知的事物，不是抽象概念
- 参考标准：更像一篇深度报道的节选、一段纪录片的核心片段、一本书的核心章节

**有形性判定标准**（供 Anchor Engine 的 EvaluateQuality 使用）：

| 类型 | 有形性判定 | 示例 |
|------|-----------|------|
| 文字 | 必须是具体的作品片段，不是抽象感悟 | ✅「《百年孤独》中"多年以后..."」 ❌「孤独是一种美」 |
| 图片 | 必须是具体的画面，不是抽象图形 | ✅「街角的咖啡馆」 ❌「温暖的色调」 |
| 视频 | 必须是具体的片段，不是概括性描述 | ✅「纪录片第 32 分钟的对话」 ❌「一部关于战争的纪录片」 |
| 声音 | 必须是具体的音频，不是文字描述 | ✅「雨声 + 钢琴曲」 ❌「一首悲伤的歌」 |
| 物件 | 必须是具体的物品，不是类别 | ✅「外婆的搪瓷杯」 ❌「旧物件」 |
| 场所 | 必须是具体的地点，不是泛指 | ✅「南京西路的季风书园」 ❌「一家书店」 |

**用户内容成为心物的逻辑**：
- 用户表达本身不是心物，用户表达中引用/描述的事物才是心物
- 例：用户写"今天在咖啡馆看到一对老夫妻，让我想起了外婆"→ 心物是"咖啡馆的老夫妻"，不是用户的感悟
- 系统识别用户表达中的"有形事物"，提取为心物素材

### 2.2 感受链模型（Feeling Chain Model）

感受链替代传统的"内容+评论"模式。关于感受链的产品哲学参见《产品理念说明书》第四章。

#### 结构定义

- **感受链是单层结构**：每条感受链条目直接附着于心物下方，不存在"感受的感受"的深层嵌套
- **每条感受链条目拥有独立 ID**：它同时作为独立心物存在，可被其他用户浏览并产生新的感受
- **感受链条目 ≠ 回复**：每条感受是用户对原心物的独立反应，不是对其他感受的回复

```
心物 X（夕阳照片）
  │
  ├─→ 感受链 A："让我想起外婆家门口的夕阳"  ← 独立心物 A
  ├─→ 感受链 B："美得让人安静"              ← 独立心物 B
  └─→ 感受链 C："这种光线下拍过一张全家福"    ← 独立心物 C

当用户点击感受链 A 进入时：
心物 A（"让我想起外婆家门口的夕阳"）
  │
  ├─→ 感受链 A1："我外婆也喜欢看夕阳"
  └─→ 感受链 A2："珍惜还在的人"
```

#### 感受链条目成为心物的条件

感受链条目自动获得独立心物 ID。其有形性继承自原始心物——感受链条目不是孤立的感受，而是"原始心物+感受"的组合体。原始心物的有形性就是感受链心物的有形性来源。

展示权重遵循与普通心物相同的规则：
- 被多人共鸣的感受链条目 → 更高展示权重
- 被标记为"未体验"的感受链条目 → 降低展示权重
- 感受链条目的质量由社区反应自然筛选

#### 与传统评论区的区别

| 维度 | 传统评论区 | 感受链 |
|------|-----------|--------|
| 结构 | 线性/树状嵌套 | 单层平铺 |
| 关系 | 回复某人 | 对心物的独立反应 |
| 语境 | 依赖上下文 | 每条自包含 |
| 深度 | 可无限嵌套 | 每条独立，可展开为新心物 |
| 焦点 | 围绕发布者 | 围绕心物 |

### 2.3 共鸣系统（Resonance System）

关于共鸣的产品哲学参见《产品理念说明书》第四章。

#### 五态反应

用户不需要选择反应类型。用户只管表达，系统自动推断。

用户表达后，系统自动推断反应类型：

| 系统推断 | 含义 | 权重 |
|----------|------|------|
| **共鸣** | "我也经历过" | 强正向 |
| **无感** | "我看到了，但没什么感觉" | 弱信号 |
| **反对** | "我不太认同" | 强负向（也是一种深度参与） |
| **未体验** | 表达内容与心物无关或缺乏真实细节 | 真实性信号 |

**有害**是唯一的例外：用户可以主动标记，但必须写理由，有成本。

**无感是默认表态**：用户看到心物后选择留下反应但没有特别感受时，系统推断为无感。与"直接滑走不操作"不同，无感是一种主动的表态——"我看到了"。在共鸣值计算中，无感作为弱信号参与，权重接近零但不为零。

#### 共鸣的情绪词细分（系统自动推断）

| 情绪词 | 含义 | 推断依据 |
|--------|------|---------|
| 同感 | "我也有同样的感受" | 表达内容与心物的情感方向一致 |
| 触发 | "让我想起了……" | 表达中包含个人经历或记忆 |
| 启发 | "没这么想过，但你说得对" | 表达中包含新视角或反思 |
| 震撼 | "说不出话" | 表达简短但情感强烈 |

**设计原则**：用户只管表达，系统负责分类。五态反应是系统内部的统计指标，不是用户界面的功能。

#### "未体验"标记的设计意图

不限制谁能发言，但通过社区标记来自然筛选不真实的分享。

- **软性约束**：不阻止任何人发表任何方向的感受，但允许其他用户标记"我认为 ta 没有体验过"
- **有成本**：和"有害"标记一样，需要写理由，不能只点按钮
- **影响权重**：被大量标记为"未体验"的内容，其"共鸣"权重会降低——不是删除，是降低影响力
- **不等于有害**："未体验"不是攻击，是对真实性的判断。大量标记为"未体验"的内容不会被屏蔽，但不会获得高共鸣权重
- **设计原则**：靠机制让真实的表达自然胜出，而非靠硬性限制谁能说

#### 内容治理机制

基于社区反应的内容治理（非平台审核员判定）：

| 触发条件 | 系统动作 |
|------|---------|
| 共鸣 vs 反对严重失衡 | 可能是争议性内容 → 降权但不屏蔽 |
| "有害"占比异常高 | 大概率恶意内容 → 屏蔽，停止扩散 |
| "未体验"占比高 | 内容真实性存疑 → 降低共鸣权重，不删除 |
| 每种状态下可留下感受 | 感受本身也受同样的治理规则约束 |

- "有害"不是"我不喜欢"，是有成本的信号，需要防止滥用
- "未体验"不是"我反对这个感受"，是对表达者真实性的判断
- 争议性内容（共鸣和反对都高）≠ 有害内容，前者保留但降权

#### 共鸣值计算逻辑

```
单心物共鸣值 = f(反应类型, 感受深度, 相关性, 增量性, 有害惩罚, 未体验惩罚)
        │
        ↓
话题内衰减：同一话题第 N 次共鸣的边际价值递减
        │
        ↓
跨话题加权：不同话题/领域的共鸣 → 权重递增
        │
        ↓
关系分 = Σ(各心物共鸣值 × 话题衰减) × 话题多样性加权
        │
        ↓
高阶体验增强 = 关系分 AND 活跃度信号（双方近期都在场）
        │
        ↓
达标 → 自然涌现沟通可能
```

**两层衰减 + 活跃度信号**：
- **话题内衰减**：同一话题第 N 次共鸣的边际价值递减——防止在一个话题上刷共鸣
- **跨话题加权**：不同话题/领域的共鸣权重递增——奖励世界观层面的深层连接
- **个性化衰减**：关系分基于两人的互动节奏随时间递减（详见4.4节），高阶体验增强还需双方近期都有活跃

### 2.4 身份系统（Identity System）

关于匿名身份的产品哲学参见《产品理念说明书》第四章。

#### 三层身份模型

```
注册阶段：强实名（手机号/真实身份验证，平台存档，永不对外暴露）
                │
                ↓
        ┌───────────────────────────────────┐
        │  一切对外展示                       │
        │  随机昵称                          │  ← 每次发言可能不同
        │  随机头像                          │  ← 系统分配
        │  无个人主页                        │  ← 无法主动查看某人历史发言
        └─────────────────┬─────────────────┘
                          │
                  共鸣积累 → 关系自然涌现
                          │
                          ↓
        ┌───────────────────────────────────┐
        │  感受知己                          │
        │  系统提示「有个人总是跟你有同样的感受」  │
        │  可见对方的「感受模式」              │
        │  不可见任何身份信息                  │
        └─────────────────┬─────────────────┘
                          │
                  双方独立表达「想认识这个人」
                          │
                          ↓
        ┌───────────────────────────────────┐
        │  匿名知己                          │
        │  互相可见「设定昵称」（非真名）       │
        │  互相可见「设定头像」（非真实照片）    │
        │  互相可见「设定简介」                │
        │  可自由对话                         │
        │  可随时退回「感受知己」或完全匿名     │
        └───────────────────────────────────┘
```

#### 核心原则：匿名性永不打破

- **强实名**：守住底线（违法、恶意行为可追溯），但永不对外暴露
- **展示全匿名**：消除社交表演压力，只看感受不看人
- **感受知己**：通过感受认识一个人，不是通过身份
- **匿名知己**：即使最深层的连接，也只展示用户自己设定的昵称和头像
- **真名永不暴露**：真名可以被搜索、可以跨平台追踪，一旦暴露无法收回

#### 为什么「设定昵称」而非「真名」？

即使在最深的知己关系中，匿名性也应该被保留：

- **真名可以被搜索** → 打破匿名性，可以在其他平台找到对方
- **真名可以跨平台追踪** → 一旦知道真名，无法「不知道」
- **真名是不可逆的** → 一旦暴露，无法收回
- **设定昵称是用户主动选择的** → 用户决定展示什么，保留控制权

知己关系的本质是「感受的连接」，不是「身份的连接」。你通过感受认识一个人，不需要知道 ta 的真名。

## 三、交互模型

### 3.1 核心交互循环

```
平台/用户提供心物（高质量、完整内容）
        │
        ↓
用户浏览、体验心物
        │
        ↓
留下感受（系统自动推断反应类型：共鸣/无感/反对/未体验）
        │
        ↓
该感受成为一条感受链条目，附着于原心物下方
        │
        ↓
每条感受链条目同时作为独立心物（拥有独立 ID）
可被其他用户浏览并产生新的感受
        │
        ↓
系统计算共鸣值（跨话题加权）
        │
        ↓
共鸣值达标 → 匿名身份下的沟通渠道自然显现
        │
        ↓
持续共鸣积累 → 可选择互相揭示固定身份
```

**心物页面交互布局**：

```
┌──────────────────────────────────┐
│  [原始心物内容]                    │
│  文字/图片/视频/声音/物件/场所      │
│                                  │
│  ── 感受链 ──                    │
│  A: "让我想起外婆家门口的夕阳"    │
│  B: "美得让人安静"                │
│  C: "这种光线下拍过一张全家福"    │
│  ...                             │
│                                  │
│  [写下你的感受...]                │
└──────────────────────────────────┘
```

每条感受链条目可以被点击进入，此时它作为独立心物展示，下方挂载基于它的新感受链。**但感受链始终只有单层——不存在"感受的感受的感受"的深层嵌套。**

### 3.2 信任递进阶梯

体验是连续的渐进增强，而非离散的功能解锁。用户不会感觉到"我解锁了新东西"，只会感觉到"这个体验越来越丰富了"。

```
L0  浏览心物 → 看到内容，可以留下反应
L1  痕迹可见 → 看到他人的匿名感受，体验感受碰撞
L2  感受回应 → 对他人感受链条目产生新感受，对方可能看到（异步）
L3  回达增强 → 回应时可选"确保对方看到"（仍异步，但有送达感）
```

**关键：每一级都是前一级的"渐进增强"，而非"新增一个功能"。**
- L0→L1：不是"解锁了看别人的感受"，而是心物下本来就有感受链条目
- L2→L3：不是"解锁了私信"，而是回应方式多了一个选项
- L0~L3 的所有交流始终在心物的上下文里，始终异步
- 唯一的例外是匿名知己的对话空间——它在知己关系建立后才出现，是心物内共鸣的自然延伸

**同时在场信号**：当两人恰好同时在同一心物下表达时，系统将此作为共鸣关系的加权信号（"此刻你们被同一个事物触动"），但不提供实时对话能力。感受链始终是异步的。

**阈值计算是双向的**——必须双方的共鸣关系分都达到阈值。系统不会告诉用户"你达到了 Level X"——体验在后台静默增强，用户在自然体验中偶然发现。

### 3.3 知己系统

#### 核心设计哲学

知己关系的本质是「通过感受认识一个人，不是通过身份」。关于知己的产品理念参见《产品理念说明书》第四章。

#### 关系深度是光谱，不是阶段

真实的关系不是二元的（连接/断开），而是连续的光谱（亲近/疏远）。

**系统内部维护一个「关系深度」光谱（0-100），但用户永远看不到这个数字。**

用户感知到的:
- 某个人的内容越来越多地出现在你的视野
- 某个人越来越频繁地与你共鸣
- 某天你突然发现：「有一个人总是跟我有同样的感受」
- 你不知道「深度」是多少，你只是... 感觉到了

**关系光谱是系统内部的，不是用户界面的。没有「共鸣深度」数字，没有「关系进度条」，没有任何指标。**

#### 升级：自然发生，不是手动操作

知己关系的升级是**自动的、基于共鸣的、无声的**：

```
完全匿名（初始状态）
    │
    │  你们在多个心物上反复共鸣
    │  系统检测到共鸣模式相似
    │  一切自动发生，你没有「选择」任何东西
    ↓
感受知己（系统自动识别）
    │
    │  系统提示：「有个人总是跟你有同样的感受」
    │  你可以看到对方的「感受模式」（匿名的）
    │  不能看到任何身份信息
    │
    │  如果双方都独立选择「想认识这个人」
    ↓
匿名知己（双向选择）
    │
    │  互相可见「设定昵称」「设定头像」「设定简介」
    │  可自由对话
    │  仍然不知道对方的真名
```

**关键原则**：
- 你没有「找知己」，你只是表达自己，然后遇到了一个跟你很像的人
- 升级是自动的，不是你选择的
- 只有「匿名知己」需要双方主动选择，其他升级都是自然发生的

#### 降级：渐进的，不是突然的

知己关系的降级是**无声的、渐进的、没有仪式感的**：

- **不是**：「断开连接」按钮（突然的，有情感成本）
- **而是**：减少互动，关系自然淡化

你不需要「做」什么来降级，你只需要「不做」什么。

- 你只是不再跟这个人共鸣
- 系统自然地减少这个人的曝光
- 关系自然地淡化
- 没有「断开」的仪式感，没有情感成本
- 对方不会收到任何通知

**降级是无声的，对方不会知道。没有「删除好友」「断开连接」的操作，只有自然的疏远。**

#### 关系容量与静默机制

**核心洞察**：每个人的精力是有限的。你可能跟 100 个人有共鸣，但你最多只能跟 5-10 个人建立深度连接。**关系深度不只是绝对值，也是相对排名。**

```
你的所有共鸣关系
    │
    │  按关系深度排名
    ↓
┌─────────────────────────────────────┐
│  前 N%：显著曝光                      │
│  在「感受知己」区域突出展示             │
│  N 基于你的互动容量，因人而异           │
└─────────────────────────────────────┘
    │
    │  排名下降
    ↓
┌─────────────────────────────────────┐
│  其他：静默                           │
│  仍然存在，但降低能见度                │
│  不是删除，不是惩罚                   │
│  只是你的注意力自然流向最强的连接       │
└─────────────────────────────────────┘
```

**静默机制的设计原则**：
- **静默不是删除**：关系仍然存在，只是降低能见度
- **静默是无声的**：对方不会知道自己被静默了
- **静默是可逆的**：如果你们再次共鸣，排名可能上升，关系恢复
- **静默是自然的**：不需要手动操作，系统自动处理
- **容量是个性化的**：基于你的互动频率，不是固定数字

**静默是关于你的注意力，不是关于关系本身。**

**N% 计算公式**：

```python
def calculate_capacity_n(user) -> float:
    """计算用户的互动容量百分比 N

    核心理念：每个人的精力是有限的。
    你可能跟 100 个人有共鸣，但你最多只能跟 5-10 个人建立深度连接。
    N 基于你的互动频率动态调整。
    """
    # 1. 计算用户的互动基线
    baseline = user.baseline  # 已有的互动基线数据

    # 2. 估算可维持的深度关系数量
    # 经验公式：每周互动次数 / 5 = 可维持的深度关系数
    # 例：每周互动 25 次 → 可维持 5 个深度关系
    weekly_interactions = baseline.avg_weekly_interactions
    max_deep_relations = max(3, min(10, weekly_interactions / 5))

    # 3. 计算 N%
    # N% = max_deep_relations / total_resonance_relations
    total_relations = len(user.resonance_relations)
    if total_relations == 0:
        return 0.0

    n_percent = max_deep_relations / total_relations

    # 4. 限制在合理范围内
    # 最小 10%（至少展示 1 个），最大 50%（不超过一半）
    return max(0.1, min(0.5, n_percent))
```

**举例**：
- 用户 A：每周互动 20 次，有 30 个共鸣关系
  - max_deep_relations = 20 / 5 = 4
  - N% = 4 / 30 = 13.3%
  - 展示前 4 个最深的关系
- 用户 B：每周互动 50 次，有 100 个共鸣关系
  - max_deep_relations = min(10, 50 / 5) = 10
  - N% = 10 / 100 = 10%
  - 展示前 10 个最深的关系

#### 知己入口的设计原则

**功能渐进显现**：知己功能不对新用户展示。只有当用户的使用达到可以建立知己关系的程度时，相应的功能窗口才会自然出现。

```
新用户（初始状态）
    │  看不到任何知己相关的 UI
    │  不知道有知己功能的存在
    │  专注于表达和共鸣本身
    ↓
共鸣积累到阈值
    │  系统检测到你已经有足够深的共鸣关系
    │  知己入口自然出现（安静地，不通知）
    │  你发现它时，里面已经有内容了
    ↓
建立匿名知己
    │  双方选择「想认识这个人」
    │  匿名知己功能显现
```

**设计原则**：
- 不在底部 Tab 栏（不是一等公民）
- 不在首页突出展示
- 入口位置：「我」页面内的一个安静条目
- 新用户看不到这个入口（功能未显现）
- 当你第一次看到它时，里面已经有内容了——那一刻的惊喜感：「原来这里有人了」
- 没有数字角标，没有引导，没有「去发现知己」的提示

#### 知己对话空间

匿名知己拥有独立的对话空间，这是 Standby 中唯一脱离心物上下文的沟通形态。

**设计原则**：
- **渐进显现**：对话空间只在知己关系建立后出现，初期用户完全不知道它的存在
- **根植于心物**：对话的起点和素材仍然是心物——知己之间可以分享心物、围绕心物交流，对话空间是心物内共鸣的自然延伸
- **不违背「有物才有真实感想」**：知己对话的根基是之前在无数心物上积累的共鸣，不是无根的闲聊
- **非一等公民**：对话空间不在底部 Tab 栏，入口在知己关系页面内

**与其他平台私聊的区别**：
| 维度 | 传统私聊 | 知己对话空间 |
|------|---------|------------|
| 出现时机 | 注册即可用 | 知己关系建立后才出现 |
| 对象选择 | 主动搜索/添加 | 通过共鸣自然涌现 |
| 身份可见 | 通常可见真名/头像 | 仅可见设定昵称/头像 |
| 内容根基 | 无要求 | 根植于心物共鸣的历史 |
| 对话起点 | 任意话题 | 通常从分享心物开始 |

### 3.4 沟通规则

- **异步为主，体验自足**：主体是时间胶囊系统，异步体验本身必须足够好——留下感想不期待被谁看到，表达本身就是价值。核心自足体验包括：

  **① 感受碰撞**：心物下的不同感受之间的碰撞本身就有价值。用户可以浏览他人留下的感受链条目——看到别人如何被同一个事物触动，这种"思想的交锋"不需要建立人际关系。每条感受链条目作为独立心物，可以继续引发新的感受。

  **② 群体记忆重现**（TBD，由运营团队规划）：当心物随时间回归（季节性、周年、社会事件回响），用户重新遇到同一个心物时，系统浮现"群体记忆"——你一年前在这个心物下的感想、当时有多少人和你感受相同、群体对这个话题的理解如何演变。**心物是记忆的触发器，没有心物的空泛时间胶囊不符合 Standby 的产品哲学（有物才有真实感想）。** 触发机制、数据模型、引擎归属待运营团队定义。

  **③ 表达即价值**：用户写下的感受本身就是对自我思考的整理。产品叙事和 UI 设计应传递"写下来就是收获"——而非"写下来等别人看到"。

- **感受链始终异步**：不提供实时对话能力，"同时在场"仅作为共鸣加权信号，不开放实时交互
- **发现是一种惊喜**：用户在自然浏览中反复遇到同一个人的感受链条目，逐渐意识到"有一个人一直在同一个频率上"——这种发现的惊喜感本身就是体验的一部分
- **不允许主动寻找目标**：用户不能搜索特定用户、不能主动发起对话。此约束防止有针对性的骚扰和有目标性的对象获取。匿名知己是唯一例外——知己关系是通过持续共鸣自然涌现的，不是"找"来的，成为匿名知己后可自由对话
- **即使永远没有发现对方，体验也是完整的**：自我表达、感受碰撞、群体记忆——这些不依赖外部连接

### 3.5 跨设备体验

**目标生态**：对小米全生态多终端统一系统（澎湃 OS）进行原生级别适配，实现多端查看、多端交互、多端分享。

**一期覆盖设备**：

| 设备 | 场景定位 | 核心交互方式 |
|------|---------|------------|
| 手机 | 碎片时间、移动场景 | 浏览心物、快速反应、轻量表达、多模态捕捉 |
| 平板 | 放松状态、深度场景 | 深度阅读、长文创作、沉浸浏览 |
| 电脑 | 书桌前、专注场景 | 长篇感想、系统性回顾、整理思考 |
| 车机 | 驾驶场景 | 语音收听、语音触发感想、情境推送 |

**跨设备的两层价值**：

#### 第一层：场景接力

用户的思考是连续的，但使用设备的场景是断续的。跨设备的核心价值之一是在场景切换时不让体验断裂。

典型接力场景：
- **触发→沉淀**：早晨通勤（手机）看到心物被击中，留下简短反应；晚上（平板）想法发酵后写下完整感想
- **收听→感受**：开车（车机）听到心物语音摘要深受触动；到达后（手机）用语音记下感受；回到家（电脑）整理成完整感受
- **浏览→分享**：在网页上看到深度文章（电脑），通过系统级分享直接导入成为心物素材（手机）
- **碎片发现→完整回顾**：手机上偶然发现熟悉风格的感想，电脑上在共鸣记录里拼出完整的共鸣轨迹

#### 第二层：多设备融合感知（核心差异化价值）

多设备并行融合能产生单一设备永远无法产生的状态理解，从而提供单一设备永远无法提供的体验质量。

**多维度状态理解**：

单一设备只能看到用户的一个切面——手机知道你在哪但不知道你在想什么，平板知道你在看什么但不知道你的情绪状态。但当多设备信号融合时：

- 手机感知你在咖啡馆 + 平板感知你正在深度浏览关于孤独的心物 + PC 感知你已连续工作 4 小时 → 系统理解"一个疲惫的人在安静的咖啡馆里被一段关于孤独的话击中了"
- 车机感知你在深夜独自开车 + 手机感知你在听一首老歌 + 平板感知你昨天写过关于回忆的感想 → 系统理解"这个人正处于怀旧的情绪状态中"

**单一设备永远无法得出这种判断。这是融合的真正价值。**

**心物的情境增强**：同一个心物在不同情境下对人的触动完全不同。多设备融合让系统理解的不只是"用户看了什么"，而是"用户在什么状态下看了什么"。心物的呈现更有温度——在对的时间、对的状态下，把对的内容送到面前。

**表达的多模态融合**：人的感受本身就是多模态的。多设备融合可以同时捕捉：手机摄像头的画面 + 耳机的音乐 + 语音记录的感受，合成为一个完整的心物素材。这个表达质量是任何单一设备都做不到的。

**共鸣的空间感知**（TBD）：当多设备感知到两个用户在物理空间上接近且浏览同一个心物时，这种"同空间 + 同心物"的信号可以在共鸣机制中加权。不需要暴露位置——只是两个在同一个咖啡馆被同一段话击中的人，他们的共鸣可能比纯线上更真实。实现方案待定：加密策略和云端计算策略需要更仔细地规划，确保不违反"原始数据不离开设备"的隐私红线。

**生活节奏同步**：多设备长时间融合感知能拼出用户的日常生活节奏——每晚 10 点后是深度阅读时间（平板）、每次通勤路上倾向快速浏览（手机）、每次开车时情绪最放松（车机）。系统在合适的节奏点上提供合适的体验，不是"产品在服务你"，而是"产品在和你同步呼吸"。

#### 与小米智能助理的深度融合

不只是通信接口，智能助理是跨设备体验的调度者：
- **情境感知**：知道用户在哪个设备上、什么状态，自动调整交互方式
- **主动推送**：根据用户习惯，在合适的设备上、合适的时间，轻推可能引发共鸣的心物
- **语音桥接**：用户说"帮我记一下"，智能助理自动关联上下文（正在听的歌、正在看的视频、正在经过的地方）
- **设备接力**：在手机上浏览到一半，智能助理建议"这个内容很适合在平板上细读"——不强制，只是轻提示

#### 隐私红线

所有融合感知必须遵循：
1. **所有原始数据不离开设备**——融合在端侧进行，只输出抽象状态，不输出原始传感器数据
2. **用户完全知情和可控**——用户可以查看"系统感知到了什么"，可以关闭任意维度的感知
3. **不对外暴露任何感知信息**——其他用户、合作方、任何第三方都无法获取
4. **感知服务于体验，不服务于商业**——不基于融合感知做广告、不做行为画像变现

**设计原则**：跨设备不是功能叠加，是让产品融入用户在不同设备间流转的日常生活。多设备融合的真正价值不是"无缝切换"，而是产生单一设备永远不可能产生的状态理解，提供单一设备永远不可能提供的体验质量。

## 四、AI 引擎定义

### 4.1 核心技术资产：五个 AI 决策引擎

Standby 的核心技术资产是五个 AI 驱动的决策引擎，它们协同工作，构成产品的技术护城河。

```
                    ┌─────────────────────┐
                    │   情境感知引擎       │
                    │ （多设备融合感知）    │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ↓                ↓                ↓
     心物生成引擎        共鸣机制引擎      内容治理引擎
     （整理客观素材）   （空间感知加权）   （情境辅助判断）
              │                │
              ↓                ↓
          用户管理引擎
       （节奏适配交互）
```

| 引擎 | 核心职责 |
|------|---------|
| 情境感知引擎 | 理解用户状态和情境（多设备融合感知） |
| 心物生成引擎 | 整理客观素材，供用户选择 |
| 共鸣机制引擎 | 计算人与人之间的共鸣 |
| 用户管理引擎 | 管理身份与关系 |
| 内容治理引擎 | 保障社区安全 |

情境感知引擎是底层感知层——其他四个引擎都从它获取情境信息，但它不直接参与内容、关系、身份或安全的决策。

**部署原则：独立部署、可解耦单独扩容**

五个引擎独立部署，通过标准化接口通信，任何一个引擎可以单独扩容而不影响其他引擎。各引擎根据负载特征采用不同的扩容策略：

| 引擎 | 扩容特征 |
|------|---------|
| 情境感知引擎 | 端侧为主（信号采集、融合计算），云端提供轻量查询服务（话题权重、跨设备同步） |
| 心物生成引擎 | 离线批处理，按素材整理量扩容 |
| 共鸣机制引擎 | 增量计算，按用户活跃度扩容 |
| 用户管理引擎 | 轻量计算，按用户总量扩容 |
| 内容治理引擎 | 端侧为主（敏感词、情绪、指纹），云端做聚合分析（模式检测、异常检测），按标记频率扩容 |

AI 引擎成本可控——端侧优先、离线批处理、增量计算、模型分级。整体运营成本不高于传统社交平台（无需养推荐算法团队、无需海量人工审核、带宽成本低）。

### 4.2 心物生成引擎

心物是客观事物，不受人情感影响。人在产生感性的瞬间，往往难以同时理清"我看到了什么、听到了什么、身处什么场景"——等这些客观素材准备好，一霎那的真实情感可能已经变淡了。

心物生成引擎的作用：**从已有世界中发现并整理有可能触发感性瞬间的客观事物，供用户选择。** 用户只需要关注自己要表达的情感是什么，不需要费力做基础性的素材准备工作。

**核心原则**：AI 准备心物（客观素材），用户表达感受（真实情感）。AI 不参与感受的生成。

**能力要求**：
- **素材整理**：从经典文学、纪录片、深度报道、历史事件、音乐等多种来源中，提取符合心物标准的客观素材
- **标准把控**：确保输出的心物完整、具体、真实，有充足的信息量和上下文
- **来源多样**：覆盖文字、图片、视频、声音、物件、场所等多种类型
- **用户辅助**：当用户引用某个事物但描述模糊时，帮助用户补充客观细节（如"你说的那本书的那段话，是这段吗？"）
- **来源标注**：标注心物的来源，保持透明

**关键约束**：
- AI 只准备客观素材，不生成、不引导、不暗示任何情感方向
- 每个心物都需要经过深度分析，保证信息密度和引发思考的空间
- 输出必须经得起时间检验——三个月后读到仍然能引发共鸣

### 4.3 情境感知引擎

底层感知层。融合多设备信号，理解用户的状态和情境，为其他引擎提供情境信息。

**核心能力**：
- **多设备信号采集**：从手机、平板、电脑、车机收集传感器和行为信号（位置、运动、使用状态、时间模式等）
- **端侧融合**：所有原始数据不离开设备，在端侧进行融合计算，只输出抽象情境状态
- **多维度状态理解**：融合多个设备的信号，推断用户的情绪状态、注意力状态、场景类型
- **生活节奏建模**：长时间学习用户的设备使用节奏和情感周期，在合适的节奏点上提供合适的内容和交互
- **空间感知**（TBD）：感知用户间的物理空间关系（不暴露位置，仅用于共鸣加权等内部计算），实现方案待定

**与其他引擎的协作**：
- 给心物生成引擎：提供情境信息，增强心物的呈现时机和方式
- 给共鸣机制引擎：提供空间感知信号，用于共鸣关系加权
- 给用户管理引擎：提供用户节奏信息，适配不同设备上的交互方式
- 给内容治理引擎：提供情境信息，辅助判断内容的上下文

**关键约束**：
- 原始数据不离开设备，只输出抽象状态
- 用户完全知情和可控——可查看感知内容、可关闭任意维度
- 不对外暴露——其他用户、合作方、第三方均无法获取
- 感知服务于体验，不服务于商业——不做广告、不做行为画像变现

### 4.4 共鸣机制引擎

发现人与人之间隐藏的共鸣，计算共鸣关系，驱动连接的自然涌现。

**核心能力**：
- **五态反应处理**：对每条心物（包括感受链条目形成的独立心物），处理用户的共鸣/无感/反对/未体验/有害五种反应
- **共鸣值计算**：基于反应类型、感受深度，计算单心物共鸣值
- **话题内衰减**：同一话题第 N 次共鸣的边际价值递减
- **跨话题加权**：不同话题/领域的共鸣权重递增，奖励世界观层面的深层连接
- **活跃度信号**：关系分个性化衰减，高阶体验增强还需双方近期都有活跃
- **关系分计算**：综合各心物共鸣值与话题多样性系数

#### 关系深度算法

##### 核心原则

1. **用相对值，不用绝对值**：关系深度 = 你们的共鸣频率 / 你的正常共鸣频率
2. **关系深度对用户不可见**：系统内部维护，用户永远看不到任何数字
3. **个性化基线**：每个用户有自己的互动节奏，衰减速率因人而异
4. **个性化衰减**：衰减速率基于两人的互动节奏，活跃用户衰减快，低频用户衰减慢
5. **容量限制**：前 N% 关系获得显著曝光，其他关系静默

##### 个性化基线

每个用户有一个「互动基线」，动态更新：

- **表达频率**：你多久表达一次？
- **共鸣频率**：你多久共鸣一次？
- **共鸣比例**：你看到的内容中，多少比例会共鸣？
- **平均互动间隔**：你的正常互动节奏是什么？

**基线是你自己的「正常水平」，不是全局标准。**

##### 相对共鸣强度

对于每对用户 (A, B)，计算「相对共鸣强度」：

```
相对共鸣强度 =
  (A 和 B 的共鸣次数) /
  (A 的正常共鸣频率 × B 的正常共鸣频率 × 时间窗口)
```

**举例**：
- A 每天表达，正常共鸣率 20%
- B 每周表达，正常共鸣率 50%
- 过去一个月，A 和 B 共鸣了 10 次
- 对 A：正常共鸣次数 = 30天 × 1次/天 × 20% = 6次 → 相对强度 = 10/6 = 1.67
- 对 B：正常共鸣次数 = 4周 × 1次/周 × 50% = 2次 → 相对强度 = 10/2 = 5.0

**同样的 10 次共鸣，对 B 来说更「特殊」。**

##### 个性化衰减

衰减基于两人的互动节奏，不是全局统一速率。活跃用户衰减更快（更频繁建立新连接，老关系自然让位），低频用户衰减更慢（每次共鸣更珍贵）。

```python
def decay_score(score, time_gap, user_a_baseline, user_b_baseline):
    """
    个性化衰减函数
    score: 当前关系分
    time_gap: 距离上次互动的时间间隔
    user_a/b_baseline: 两人的互动基线
    """
    # 取两人中更活跃的作为衰减基准（更活跃的人更快"淡忘"）
    avg_interval = min(user_a_baseline.avg_interval,
                       user_b_baseline.avg_interval)

    # 1个周期内不衰减（grace period）
    periods = time_gap / avg_interval
    if periods <= 1.0:
        return score

    # 半衰期：活跃用户~5周期，低频用户~20周期，基准~10周期
    half_life_periods = max(5, min(20, 10 * (avg_interval / 7)))

    decay_factor = 0.5 ** ((periods - 1) / half_life_periods)
    return score * decay_factor
```

**衰减效果示例**：

| 用户类型 | 平均互动间隔 | grace period | 半衰期 | 沉默3个月后分数 |
|---------|:---:|:---:|:---:|:---:|
| 日活用户 | 1天 | 1天 | ~10天 | 降至 ~1% |
| 周活用户 | 7天 | 7天 | ~10周 | 降至 ~50% |
| 月活用户 | 30天 | 30天 | ~10月 | 降至 ~80% |

##### 跨时空共鸣

Standby 不是热点式平台。心物是永恒的——一段文字、一张照片、一个场所，三个月后和今天同样能触动人心。两个人在不同时间对同一心物产生共鸣，是真实的共鸣，不应被时间差惩罚。

**跨时空共鸣的识别**：

当用户 A 对心物 X 产生共鸣时，系统查询心物 X 的所有历史共鸣者（包括数月前共鸣过的用户 B）。即使 A 和 B 从未在同一时间段互动，只要他们的感受向量相似度超过阈值，就产生一次跨时空共鸣事件。

```
用户B 三个月前对心物X共鸣：「让我想起外婆」
用户A 今天对心物X共鸣：「想起小时候外婆家的院子」
    │
    ↓
感受向量相似度 > 阈值 → 跨时空共鸣成立
    │
    ↓
关系分增量 = 基础共鸣值 × 跨时空加权系数
跨时空加权系数 ≥ 1.0（跨时空共鸣不打折扣）
```

**与常规衰减的关系**：
- 常规衰减适用于"两人互动频率下降"的场景——关系因缺乏维护而淡化
- 跨时空共鸣适用于"两人从未同时在场但对同一事物有共鸣"的场景——这是 Standby 独有的共鸣形式
- 两种场景不冲突：衰减惩罚的是"关系维护的懈怠"，跨时空共鸣奖励的是"感受的深层一致性"

**关键约束**：
- 跨时空共鸣只在心物层面发生，不在用户层面——系统不主动向 B 推送"A 也共鸣了"，而是在 B 的自然浏览中让这种连接被发现
- 跨时空共鸣不改变衰减规则——如果 A 和 B 后续建立了常规互动关系，正常进入衰减周期
- 跨时空加权系数不对外暴露

##### 事件流实时计算

每次用户产生共鸣事件，实时更新涉及的所有配对关系分。

**数据模型**：
- **共鸣事件**（不可变，追加写入）：user_id, seedstone_id, reaction_type, emotion_word, embedding, depth_score, timestamp
- **用户互动基线**（可变，定期更新）：user_id, avg_interval, resonance_rate, weekly_interactions, last_active_at
- **关系分缓存**（可变，事件驱动更新）：user_a, user_b, score, last_interaction_at, last_decay_at, shared_count, topic_diversity

**单次事件处理流程**：

```
用户A 对 心物X 产生共鸣
    │
    ↓
① 写入共鸣事件（O(1)）
    │
    ↓
② 查询心物X的其他共鸣者 {B1, B2, ...Bn}
   （索引：seedstone_id → [user_ids]，O(1)）
    │
    ↓
③ 对每个 Bi，计算增量共鸣值（O(n)）
   delta = f(A的反应, Bi的反应, 话题相关性, 历史关系分)
    │
    ↓
④ 更新关系分缓存（O(n)）
   new_score = old_score × decay_factor(A,Bi,time_gap) + delta
    │
    ↓
⑤ 如果 new_score 触发知己阈值 → 进入知己检测流程
```

**单事件复杂度**：O(R_x)，R_x = 心物X的共鸣者数量

**规模估算**（10万用户，10万心物，平均每人50次共鸣）：

| 场景 | 心物共鸣者 R_x | 单事件处理量 | 可行性 |
|------|:---:|:---:|------|
| 普通心物 | ~50 | 50次更新 | 轻松 |
| 热门心物 | ~500 | 500次更新 | 可控 |
| 爆款心物 | ~5000 | 需限流 | 见下方策略 |

**爆款限流**：当 R_x > 1000 时，只实时更新 A 的"活跃知己候选"（前N%关系），其余配对延迟到每日批量任务处理。

**关系分更新公式**：

```
new_score = old_score × decay_factor + delta

其中：
  decay_factor = 0.5 ^ (time_gap / half_life)
  delta = reaction_weight × depth × relevance × novelty
```

##### 关系容量与静默

```
计算所有关系的深度
    │
    │  按深度排名
    ↓
前 N%：显著曝光（在「感受知己」区域突出展示）
    │
    │  N 基于你的互动容量，因人而异
    │  容量 = 你能维持的深度关系数量
    │  基于你的互动频率动态调整
    ↓
其他：静默（存在但降低能见度）
```

**静默不是删除，是注意力分配。被静默的关系可以随时恢复（再次共鸣即可）。**

**关键约束**：
- 共鸣值不公开显示，没有排行榜
- 不做"你可能认识的人"推荐
- 共鸣痕迹的呈现遵循"自然涌现"原则——不主动推送，让用户自行发现
- 关系深度对用户完全不可见，没有进度条、没有数字、没有排名

### 4.5 用户管理引擎

管理身份与关系，驱动知己关系的自然涌现。

**核心能力**：
- **匿名身份管理**：随机昵称生成、随机头像分配、身份信息隔离
- **信任等级计算**：基于关系深度和活跃度的体验增强管理
- **知己关系管理**：共鸣模式检测、知己匹配、关系状态维护
- **用户节奏适配**：基于情境感知引擎的信号，适配不同设备上的交互方式

### 4.6 内容治理引擎

保障社区安全，维护表达的真实性。采用端侧+服务端混合治理架构。

**端侧治理（设备端完成）**：
- **敏感词检测**：本地维护敏感词库，原始内容不上服务器
- **情绪分类**：端侧模型判断情绪方向（正面/负面/中性），上传分类结果
- **内容指纹**：提取内容的抽象特征向量，用于服务端的模式匹配
- **初步风险评估**：端侧对"有害"标记内容做初步分析，上传分析结果而非原始内容

**服务端治理（基于抽象特征）**：
- **五态反应处理**：处理共鸣/无感/反对/未体验/有害标记
- **模式检测**：基于内容指纹的聚合分析，识别刷量、协调攻击等异常模式
- **异常行为检测**：基于行为特征（时间模式、反应模式、设备模式）的异常检测
- **分级响应**：观察→降权→暂停→移除的梯度处理

**关键约束**：
- 服务端不持有可读的原始表达内容
- 治理决策基于抽象特征和元数据，不基于内容原文
- "有害"标记的复核流程：端侧初步分析 → 服务端模式匹配 → 人工复核（仅在极端情况下，且需多层审批）

## 五、内容治理

### 5.1 "有害"信号防滥用机制

**核心矛盾**："有害"信号需要够灵敏以识别真正有害的内容，同时够防弹以防止成为压制异见的武器。最危险的不是攻击本身，而是用户感知到风险后的寒蝉效应。

#### 标记有成本

- **必须写理由**：不能只点按钮，必须输入说明为什么认为有害（最低字数要求）
- **标记者可审计**：对外匿名，但系统记录标记者的实名身份，恶意标记可追责

#### AI 前置分析，不做最终裁决

采用端侧+服务端混合分析架构：

**端侧分析**（原始内容留在设备上）：
- 敏感词检测：本地维护敏感词库，匹配结果上传
- 情绪分类：端侧模型判断情绪方向，上传分类标签
- 内容指纹：提取抽象特征向量，用于服务端模式匹配

**服务端分析**（基于抽象特征）：
- 标记模式分析：检测"有害"标记是否呈现异常聚集模式
- 标记者信用评估：基于历史准确率的权重计算
- 协调攻击检测：基于行为特征的异常模式识别

**关键约束**：服务端不持有可读的原始内容，所有分析基于端侧上传的抽象特征和元数据。

#### 分级响应，而非二元处理

| 阶段 | 触发条件 | 系统动作 |
|------|---------|---------|
| 观察 | 少量有害标记 | 不做任何处理，记录 |
| 降权 | 有害标记达到阈值 + AI 初步确认 | 降低可见度，但不屏蔽 |
| 暂停 | 有害标记继续增加 + AI 高置信度 | 暂停传播，进入复核 |
| 移除 | 复核确认有害 | 移除，通知标记者结果 |
| 反转 | 复核确认无害 | 恢复，消耗标记者在"降权"阶段的信用 |

#### 标记者信用体系

- **历史准确率**：过去标记被复核为正确的比例越高，权重越大
- **反噬机制**：标记被复核为"无害"，标记者信用下降
- **严重滥用惩罚**：多次恶意标记 → 降低标记权重 → 限制标记权限
- 信用体系不对外暴露，避免博弈

#### 共鸣与有害的冲突检测

如果一条内容同时获得大量"共鸣"和大量"有害"标记：
- 不直接删除
- 触发分歧标注：系统自动标注"此内容引发较大争议，有 X% 的人共鸣，Y% 的人认为有害"
- 让用户自行判断

**争议 ≠ 有害。系统不代替用户做判断。**

## 六、安全体系

### 6.1 五层安全架构

关于安全架构的产品哲学参见《产品理念说明书》第四章。以下是各层的实现细节。

```
硬件身份 → 一人一号，攻击成本极高
    ↓
端到端通信 → 外部完全隔绝
    ↓
盲服务器 → 内部也无法窥探
    ↓
完全匿名 → 用户之间无从知晓彼此
    ↓
群体监测 → 漏网操纵行为被统计过滤
```

**没有任何单一实体能同时看到「谁说了什么」。**

### 6.2 各层实现详解

**第一层：硬件身份验证**
- 设备级硬件 ID 绑定，一人一号
- 硬件 ID 经不可逆变换后作为身份凭证，平台不持有原始硬件标识
- 攻击成本从「写脚本批量注册」变成「购买大量物理设备」

**第二层：端到端通信**
- 完全切断通过互联网端口访问中心服务器的可能
- 服务器与用户设备仅通过端到端加密通道通信
- 外部爬虫、API 滥用、中间人攻击在架构上不可行
- 匿名路由（MVP 阶段）：批量上传 + 随机延迟 + Oblivious HTTP，隐藏通信模式和请求来源

**第三层：盲服务器处理**
- 用户原始表达不上服务器，仅在端侧完成初步分析后上传抽象特征
- 端侧分析：敏感词检测、情绪分类、内容指纹提取——原始内容留在设备上
- 服务端分析：基于抽象特征的聚合分析（模式检测、异常检测、群体行为分析）
- 群体共识的聚合在特征层面完成，服务器不持有可读的原始表达
- 即使服务器被入侵、被扣押、被内部人员接触，泄露的只有抽象特征，无法还原原始内容

**第四层：完全匿名**
- 用户之间完全匿名，无用户名、无头像、无可关联身份的任何信息
- 表达内容不可追溯到任何个体

**第五层：群体行为监测（防水军）**
- 在无搜索、无话题、无趋势的环境下，真实群体表达应呈现渐进、平稳、无突变的分布
- 突变型动向（突然高峰、突然集中）几乎必然是外部操纵，自动过滤不展示
- 真实世界事件引发的自然突变与人为操纵的区分：真实事件影响多维度表达，操纵通常集中在单一维度

### 6.3 数据最小化原则

- 只收集必要的数据
- 数据在本地处理，只上传抽象状态
- 用户可以随时删除自己的所有数据
- 不对外提供任何个体数据

## 七、数据指标

### 7.1 指标哲学

留存率、注册量、使用时长是**结果**，不是目标。追逐这些指标会导致讨好用户的设计，背离「真实表达」的产品哲学。

### 7.2 四层指标体系

#### 第一层：参与度（用户是否在用）

| 指标 | 含义 | 追踪方式 |
|------|------|---------|
| 反应率 | 看心物后留下反应的比例 | 观测，期望 > 40% |
| 感受表达率 | 留下感受文字的比例 | 观测，期望 > 20% |
| 感受碰撞参与率 | 看到他人感受后产生新感受的比例 | 观测 |

#### 第二层：核心价值（共鸣是否发生）

| 指标 | 含义 | 追踪方式 |
|------|------|---------|
| L3+ 关系达成率 | 多少用户对达到 L3 以上 | 一期追踪，不设目标 |
| 知己建立率 | 知己关系的建立数量和趋势 | 一期追踪，不设目标 |
| 首次共鸣发现天数 | 从首次反应到发现共鸣痕迹的平均天数 | 观测 |

#### 第三层：体验自足（底座是否稳固）

| 指标 | 含义 | 追踪方式 |
|------|------|---------|
| 无共鸣用户 D7 留存 | 没有共鸣关系的用户是否仍然留下来 | 期望 > 25%，验证自足体验 |
| 群体记忆参与率 | 用户在心物重现时的互动比例 | 观测 |
| 表达自足率 | 不期待被看到但仍留下感受的用户比例 | 观测 |

#### 第四层：成功验证（飞轮是否转起来）

| 指标 | 含义 | 追踪方式 |
|------|------|---------|
| 用户心物通过率 | 用户内容被识别为有心物价值的比例 | 观测趋势 |
| 用户心物表现对比 | 用户心物 vs 平台心物的反应数/共鸣率/感受表达率 | **无显著差异 = 飞轮转了** |
| 用户心物占比趋势 | 用户自产心物在总心物中的月度占比 | 观测上升趋势 |

**最终检验标准**：当用户自产的心物和平台初始心物在各项表现指标上没有显著差异时——产品成功了。

### 7.3 结果指标（仅观测，不追逐）

| 指标 | 说明 |
|------|------|
| D1/D7/D30 留存 | 机制运转的结果，不是目标 |
| 注册量 | 产品的自然结果 |
| 日均使用时长 | 不追求最大化，体验自足即可 |

## 八、产品决策记录

| # | 决策 | 理由 |
|---|------|------|
| 1 | 心物由平台提供 + 用户内容生成 + AI 聚合三种来源 | 平台初始心物解决冷启动；用户内容保证原生多元；AI 聚合形成有机循环 |
| 2 | 心物需要完整、有信息量，不做碎片化 | 只有充足的信息量才能引发深层共鸣 |
| 3 | 五态反应：共鸣/无感/反对/未体验/有害 | "反对"也是深度参与；"有害"是治理信号；"未体验"是对真实性的软性筛选；无感是默认表态 |
| 4 | 共鸣值按话题衰减、跨话题加权；关系分个性化衰减；高阶体验增强需活跃度信号 | 奖励深层连接；衰减速率因人而异，高阶体验增强需双方在场；共鸣发生在心物层面（包括感受链条目形成的独立心物）；跨时空共鸣不被衰减惩罚 |
| 5 | 强实名注册 + 全匿名展示 | 守住底线同时消除表演压力 |
| 6 | 无个人主页、不可主动搜索用户 | 避免骚扰，保护匿名表达的安全感 |
| 7 | 沟通渠道由共鸣值自然显现 | 信任是挣来的，不是默认的；不是付费解锁，是行为驱动的体验增强 |
| 8 | 感受链始终异步，不提供实时对话 | 感受链中每条表达都是独立的，实时对话不适用；"同时在场"仅作为共鸣加权信号 |
| 9 | AI 做守护者和织网者，不参与感受生成 | AI 准备心物（客观素材），用户表达感受（真实情感）。AI 不生成、不引导、不暗示情感方向 |
| 10 | 跨设备系统级输入 | 让表达变得无感，融入生活 |
| 11 | 商业模式：跨设备生态合作 + 咨询服务 + 真实需求数据变现 | 不卖数据、不做广告、不搞会员分级 |
| 12 | "有害"标记必须写理由 | 增加标记成本，防止冲动滥用 |
| 13 | 分级响应而非二元删除 | 降权→暂停→移除逐级处理，给系统留缓冲空间 |
| 14 | 共鸣/有害冲突检测 | 争议 ≠ 有害，系统不代替用户做判断 |
| 15 | 标记者信用体系不对外暴露 | 防止用户博弈信用分数 |
| 16 | 同时在场作为共鸣信号，不开放实时对话 | 两人恰好同时在同一心物下表达，系统将此作为共鸣关系的加权信号 |
| 17 | 跨设备首选小米澎湃 OS 生态 | 原生级别适配四端，与小爱同学双向通信 |
| 18 | 核心技术资产为五个 AI 决策引擎 | 情境感知、心物生成、共鸣机制、用户管理、内容治理五引擎协同 |
| 19 | 心物生成引擎必须深度分析 | 不做简单搬运，每个素材经过深入理解和重构；AI 角色是整理已有世界的客观素材，不是生成新内容 |
| 20 | 跨设备体验分两层：场景接力 + 融合感知 | 场景接力解决体验断裂，融合感知产生单一设备无法提供的状态理解 |
| 21 | 五态反应：共鸣/无感/反对/未体验/有害 | 不硬性限制发言资格，通过社区标记自然筛选不真实分享 |
| 22 | 五个引擎独立部署、可解耦单独扩容 | 标准化接口通信，各引擎按负载特征独立扩容 |
| 23 | 知己关系是「感受知己」，不是「身份知己」 | 即使最深连接也只展示用户设定的昵称/头像，真名永不暴露 |
| 24 | 关系深度是光谱，不是阶段 | 系统内部维护 0-100 的关系深度光谱，用户永远看不到 |
| 25 | 升级/降级是自然发生的 | 没有「断开连接」的操作，没有情感成本 |
| 26 | 个性化基线 + 相对共鸣强度 | 每个用户有自己的互动基线，关系深度基于相对共鸣强度 |
| 27 | 个性化衰减而非统一衰减 | 衰减速率基于两人互动节奏，活跃用户衰减快，低频用户衰减慢，grace period内不衰减 |
| 28 | 关系容量与静默机制 | 前 N% 关系获得显著曝光，其他关系静默（降低能见度但不删除） |
| 29 | 性能优化：事件流实时计算 | 每次共鸣事件实时更新所有涉及配对的关系分（O(R_x)），爆款心物限流（R_x>1000 时只更新前N%关系），用户查询走缓存（O(1)） |
| 30 | 功能渐进显现 | 知己功能不对新用户展示，共鸣积累到阈值后自然出现；不是特权分级，是体验的自然丰富 |
| 31 | 知己入口在「我」页面内 | 不是独立 Tab，入口在「我」页面内的一个安静条目 |
| 32 | 感受链为单层结构，每条感受链条目形成独立心物 | 避免深层嵌套导致的复杂性；每条感受都是对原心物的独立反应，而非对其他感受的回复；感受链条目拥有独立 ID，可被其他用户浏览并产生新感受 |
| 33 | 删除"共鸣预感"功能 | 用户通过浏览感受链条目自然感知共鸣，无需额外的数字提示；保持"关系深度对用户不可见"的一致性 |
| 34 | 混合治理架构：端侧初步分析 + 服务端聚合分析 | 原始内容不上服务器，端侧做敏感词/情绪/指纹分析，服务端基于抽象特征做模式检测和异常检测；维护"盲服务器"安全承诺的同时实现内容治理 |
| 35 | 跨时空共鸣不被衰减惩罚 | Standby 不是热点式平台，心物是永恒的；两人在不同时间对同一心物的共鸣是真实共鸣，跨时空加权系数 ≥ 1.0；衰减惩罚的是关系维护的懈怠，不是共鸣的时间差 |
| 36 | 匿名知己拥有独立对话空间 | 唯一脱离心物上下文的沟通形态；渐进显现，知己关系建立后才出现；初期用户完全不知道此功能存在；根植于心物共鸣历史，不是无根闲聊 |
