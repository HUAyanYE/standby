## 一、需求回顾

Standby 五层安全架构对加密的需求：

| 层级 | 需求 | 加密技术要求 |
|------|------|-------------|
| 第一层：硬件身份 | 设备级硬件 ID 绑定，一人一号 | 不可逆变换（哈希） |
| 第二层：端到端通信 | 外部完全隔绝 | E2EE 密钥协商 + 消息加密 |
| 第三层：盲服务器 | 服务器只能看到加密数据 | 同态加密 / TEE / MPC |
| 第四层：完全匿名 | 表达不可追溯到个体 | 匿名路由 + 去身份化 |
| 第五层：群体监测 | 加密状态下聚合共识 | 同态加密 / 安全聚合 |

**核心矛盾**：既要端到端加密（服务器看不到数据），又要在服务器上完成群体共识聚合（服务器需要计算数据）。这是加密技术选型的核心挑战。

## 二、各平台加密方案分析

### 2.1 Signal 协议

**定位**：端到端加密的黄金标准，已被 WhatsApp（20亿用户）大规模验证。

**协议栈**：

| 子协议 | 功能 |
|--------|------|
| X3DH (Extended Triple Diffie-Hellman) | 异步密钥协商 |
| Double Ratchet (双棘轮算法) | 持续密钥派生 |
| Sesame | 多设备会话管理 |

**核心算法**：

```
密钥协商:  Curve25519 (ECDH)
对称加密:  AES-256-GCM
密钥派生:  HKDF-SHA256
签名:     Ed25519
```

**X3DH 密钥协商**（解决异步问题）：

```
Alice 计算四个 DH 值:
  DH1 = X25519(IK_A,  SPK_B)   // 身份绑定
  DH2 = X25519(EK_A,  IK_B)    // 防伪造
  DH3 = X25519(EK_A,  SPK_B)   // 前向保密
  DH4 = X25519(EK_A,  OPK_B)   // 额外保护

SK = HKDF(DH1 || DH2 || DH3 || DH4)
```

**Double Ratchet 算法**：

```
两个独立棘轮:
├── DH Ratchet (非对称): 消息方向切换时转动，生成新根密钥
└── Symmetric Ratchet (对称): 每条消息转动，派生消息密钥

Chain Key[n] → HMAC(CK, 0x01) → Message Key[n] (加密消息)
            → HMAC(CK, 0x02) → Chain Key[n+1] (继续棘轮)
```

**前向保密**：每条消息使用独立密钥，密钥用后即销毁。即使长期密钥泄露，过去的消息仍安全。

**后向保密**（Break-in Recovery）：DH 棘轮转动后，新的 DH 密钥交换产生全新密钥材料，恢复安全性。

**PQXDH（2023 后量子扩展）**：

```
X3DH:   4 个 DH 计算 → SK
PQXDH:  3 个 DH + 1 个 Kyber-1024 KEM → SK
```

**群聊方案**：MLS（Messaging Layer Security，IETF RFC 9420）

```
基于二叉树的密钥分发:
                    Root Key
                   /         \
              Internal       Internal
             /    \         /    \
          Alice  Bob    Charlie David

每个叶节点 = 成员密钥贡献
根节点 = 群共享密钥
O(log n) 复杂度
```

**Sealed Sender（密封信封）**：服务端甚至不知道消息发送者，只知道接收者（用于路由）。

**优点**：
- 前向保密 + 后向保密完备
- 异步通信支持
- IETF 标准化（MLS）
- 大规模验证（WhatsApp 20 亿用户）
- 开源实现（libsignal）

**缺点**：
- 强依赖中心化服务器
- 电话号码绑定身份（Standby 需要去除）
- 无内置匿名路由
- 无加密状态计算能力

**对 Standby 的适用性**：★★★★★（通信层） / ★☆☆☆☆（盲服务器聚合）

### 2.2 WhatsApp

**定位**：基于 Signal 协议的最大规模工程实现（20+ 亿用户）。

**核心技术**：

| 特性 | 实现 |
|------|------|
| 基础协议 | Signal Protocol（libsignal） |
| 密钥协商 | X3DH |
| 消息加密 | Double Ratchet + AES-256-GCM |
| 群聊加密 | Sender Keys → MLS（迁移中） |
| 密钥透明度 | Key Transparency（2023） |
| 云备份 | Advanced Data Protection（E2EE 备份） |

**Key Transparency（密钥透明度，2023）**：

```
问题: 用户如何验证服务器分发的公钥未被篡改？

方案: 可验证的公开目录（Merkle Tree）
- 所有用户的公钥哈希构成 Merkle Tree
- 任何人可验证某个公钥是否在目录中
- 服务器无法为用户 A 分发伪造的公钥而不被发现

类似 Certificate Transparency 的思路
```

**Advanced Data Protection（云备份 E2EE）**：

```
传统: WhatsApp 备份到 Google Drive/iCloud → 服务商可读
新方案: 备份密钥在用户设备生成 → 备份内容 E2EE → 云服务商无法解密
密钥恢复: 通过 64 位恢复密钥或硬件安全密钥
```

**已知问题**：
- 元数据仍暴露给 Meta（谁和谁通信、何时、频率）
- 云备份 E2EE 是可选功能，默认关闭
- 群聊成员变化时 Sender Key 重分发存在窗口期

**对 Standby 的参考价值**：Key Transparency 的思路可用于 Standby 的公钥分发验证。

### 2.3 Telegram MTProto

**定位**：Telegram 自研加密协议，效率优先。

**两种模式**：

| 模式 | 加密方式 | 服务器可见性 |
|------|---------|-------------|
| Cloud Chat（默认） | 客户端↔服务器加密 | **服务器可读** |
| Secret Chat | 端到端加密 | 服务器不可读 |

**MTProto 2.0 核心算法**：

```
密钥协商:  DH（大素数群，非椭圆曲线）
对称加密:  AES-256-IGE（争议）/ CTR（新场景）
密钥派生:  HKDF-SHA256
消息认证:  SHA-256 HMAC
```

**Secret Chat 密钥交换**：

```
1. Alice 生成临时 DH 密钥对
2. Alice → Server → Bob: 发送公钥
3. Bob 生成临时 DH 密钥对
4. Bob → Server → Alice: 发送公钥
5. 双方计算共享密钥
6. 通过可视化验证码（QR码）验证密钥
```

**安全争议**：

| 问题 | 说明 |
|------|------|
| IGE 模式 | 学术论文指出对密文篡改抵抗力弱（2015 Biryukov） |
| 非标准化 | 未经 NIST/IETF 标准化 |
| 服务器信任 | Cloud Chat 中服务器可读所有消息 |
| Secret Chat 限制 | 不支持多设备同步、群聊 |
| 密钥验证 | 依赖用户手动比对，普通用户常忽略 |

**2016 年审计**（University of London）：MTProto 1.0 存在密钥生成漏洞，2.0 已修复但非标准设计增加风险。

**对 Standby 的适用性**：★☆☆☆☆ — 不推荐。非标准化、服务器默认可读、无盲服务器支持。

### 2.4 Apple iMessage

**定位**：Apple 生态内的私有加密方案。

**核心技术**：

| 特性 | 实现 |
|------|------|
| 密钥协商 | 椭圆曲线（ECDSA-P256 + ECDH） |
| 消息加密 | AES-CTR + HMAC-SHA256 |
| 密钥托管 | Apple 服务器托管公钥目录 |
| 后量子 | PQ3（2024，Kyber-1024） |

**密钥 Escrow 争议**：

```
问题: Apple 在密钥目录中的角色
- Apple 维护所有用户的公钥目录
- 理论上 Apple 可以为用户 A 注入伪造公钥
- 攻击者（或政府）可迫使 Apple 执行 MITM

Apple 的回应:
- 2024 年推出 Contact Key Verification
- 用户可线下验证对方的公钥指纹
- 检测到不匹配时告警
```

**Contact Key Verification**：

```
用户 A 和用户 B 线下见面:
1. 双方打开"联系人密钥验证"
2. 显示公钥指纹（QR 码或数字串）
3. 比对是否一致
4. 不一致 → 可能存在 MITM 攻击
```

**PQ3 后量子加密（2024）**：

```
相比 Signal 的 PQXDH:
- PQ3 在会话期间持续使用后量子密钥（不仅仅是初始握手）
- 每条消息都包含后量子密钥材料
- 更强的后量子保护，但开销更大
```

**对 Standby 的参考价值**：PQ3 的持续后量子保护思路值得参考；密钥验证机制可用于知己关系的密钥确认。

### 2.5 Matrix Olm/Megolm

**定位**：开源去中心化端到端加密方案。

**Olm（1:1 私聊）**：

```
基于 Signal Double Ratchet 的变体:
- Curve25519 密钥交换
- Triple Ratchet 设计（发送/接收/共享三个棘轮）
- HKDF-SHA256 密钥派生
```

**Megolm（群聊）**：

```
Sender Key 模式:
- 每个群成员维护独立的 sender key
- 通过 Olm 安全通道分发给其他成员
- 单向棘轮链: R(i+1) = HKDF(R(i)) → 消息密钥

效率: O(1) 每条消息（vs Olm 的 O(n)）

安全隐患:
- 无前向保密: sender key 泄露 → 所有历史消息可解密
- 后向保密仅通过棘轮推进实现
```

**Cross-Signing（交叉签名）**：

```
密钥层级:
├── Master Key (Ed25519): 用户身份长期密钥
├── User Signing Key: 签署其他用户的主密钥（信任网）
├── Self-Signing Key: 签署自己的设备密钥
└── Device Key: 每个设备的密钥

信任模型: TOFU + 交叉签名验证
```

**优缺点**：

| 优点 | 缺点 |
|------|------|
| 开源去中心化 | Megolm 无前向保密 |
| 联邦架构 | 复杂的密钥管理 |
| Cross-Signing 信任网 | 性能不如 Signal |
| 可自托管 | 安全审计较少 |

**对 Standby 的适用性**：★★★☆☆ — 去中心化思路可参考，但 Megolm 的前向保密缺陷不适合 Standby 的安全要求。

### 2.6 同态加密 (FHE)

**定位**：在加密数据上直接计算，无需解密。盲服务器聚合的核心技术。

**主流方案对比**：

| 方案 | 数据类型 | 核心特点 | Bootstrapping 时间 |
|------|---------|---------|-------------------|
| **BFV** | 精确整数 | 直接整数映射 | 5-30 分钟 |
| **BGV** | 精确整数 | 细粒度噪声控制 | 5-30 分钟 |
| **CKKS** | 近似浮点 | SIMD 批处理 | 1-10 分钟 |
| **TFHE** | 二进制 | 位级操作 | ~13ms |

**数学基础**：全部基于 RLWE（Ring-Learning With Errors）问题。

```
多项式环: Z[X]/(X^n + 1)
安全参数: λ=128, q/B ≥ 2^128

噪声增长:
  乘法: B' ≈ B² + B·t·(N/2)
  深度 L 层: B_final ≈ B_init^(2^L)
  → 需要 q > t^(2^L) · B_init^(2^L)
```

**Bootstrapping（核心瓶颈）**：

```
作用: 同态解密再加密，刷新噪声
原理: Enc(m, pk) → Eval(Dec, Enc(sk), Enc(m)) → Enc'(m, pk')

问题: 这是 FHE 的性能瓶颈
- BFV/BGV: 5-30 分钟
- CKKS: 1-10 分钟
- TFHE: ~13ms（但只支持位操作）
```

**硬件加速趋势**：

```
2024-2025 进展:
- Intel HEXL / AMD HElib 硬件加速
- GPU 加速 (CUDA): 乘法降至 <10ms
- 专用 FHE 芯片: DARPA DPRIVE 项目
- TFHE bootstrapping: 13ms（可用）
```

**对 Standby 的适用性**：

```
场景: "用户表达在加密状态下聚合为群体共识"

可能的方案:
1. TFHE (位级): 适合投票/分类场景，bootstrapping 13ms 可接受
2. CKKS (浮点): 适合情感分析/数值聚合，但 bootstrapping 分钟级
3. 混合方案: 粗粒度用 FHE，细粒度用 TEE

实际评估:
- 简单聚合（如投票计数）: TFHE 可行
- 复杂计算（如情感分析）: FHE 不现实，需要 TEE 或 MPC
```

### 2.7 小米 MiTEE

**定位**：小米自研的可信执行环境方案，基于 ARM TrustZone。

**技术架构**：

```
ARM TrustZone 安全扩展:
├── Normal World (EL1/EL0): 普通操作系统
└── Secure World (EL1-S/EL0-S): TEE 环境
    ├── Trusted OS (OP-TEE 定制)
    ├── Trusted Applications (TA)
    └── 硬件隔离的内存/外设

MiTEE 定制:
- 基于 OP-TEE 的小米定制版本
- 安全启动链验证
- 密钥管理服务
- 生物特征数据保护
```

**主要应用场景**：

| 场景 | 说明 |
|------|------|
| 移动支付 | 小米支付的安全交易 |
| 生物识别 | 指纹/面部数据保护 |
| 密钥存储 | 硬件级密钥保护 |
| DRM | 内容版权保护 |
| 联邦学习 | 本地模型更新保护 |
| 广告隐私 | TEE 内用户画像计算 |

**TEE 在隐私计算中的角色**：

```
传统方案: 用户数据 → 服务器明文处理
TEE 方案: 用户数据 → TEE 内解密计算 → 结果加密输出

优势:
- 服务器管理员无法看到计算过程
- 硬件级隔离，比纯软件方案更可信
- 性能接近明文计算（vs FHE 的数个数量级差距）

劣势:
- 依赖硬件信任（Intel/ARM 是可信第三方）
- 侧信道攻击（Cache-out, Spectre 变体）
- TEE 并非万能——内存带宽侧信道仍需软件防护
```

**与业界对比**：

| 维度 | MiTEE | 华为 iTrustee | Intel SGX | ARM TrustZone |
|------|-------|---------------|-----------|---------------|
| 基础 | ARM TZ + 定制 | ARM TZ + 定制 | x86 TEE | ARM TZ |
| 安全等级 | 相关认证 | CC EAL5+ | 相关认证 | 基础 |
| 应用范围 | 小米生态 | 华为生态 | 通用服务器 | 通用移动端 |
| Enclave 大小 | 受限 | 受限 | 256MB~1GB | 受限 |

**对 Standby 的适用性**：★★★★☆

```
优势:
- 如果目标是小米生态，MiTEE 是天然选择
- 性能远优于 FHE（接近明文计算）
- 可用于盲服务器聚合（数据在 TEE 内解密计算）
- 跨设备 SDK 可利用小米 TEE 生态

劣势:
- 依赖小米硬件（非通用方案）
- 侧信道攻击风险
- 技术细节公开有限
```

## 四、Standby 技术选型建议

### 4.1 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    Standby 加密分层架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  Layer 1: 通信加密 (Signal Protocol)                          │
│  ├── X3DH + Double Ratchet: 1:1 知己通信                      │
│  ├── MLS: 群组密钥分发                                        │
│  ├── Sealed Sender: 隐藏发送者                                │
│  └── 修改: 去除电话号码依赖，改用设备指纹                       │
│                                                               │
│  Layer 2: 匿名路由 (待设计)                                    │
│  ├── 混淆网络 / mixnet: 隐藏通信模式                           │
│  ├── Oblivious HTTP: 请求去关联                                │
│  └── 可选: Tor / 自建匿名网络                                  │
│                                                               │
│  Layer 3: 盲服务器计算 (MiTEE + FHE 混合)                      │
│  ├── TEE (MiTEE): 通用计算场景                                 │
│  │   - 共鸣检测、情感分析、关系计算                             │
│  │   - 数据在 TEE 内解密 → 计算 → 加密输出                     │
│  ├── FHE (TFHE): 简单聚合场景                                  │
│  │   - 投票计数、分类统计                                      │
│  │   - 纯加密计算，无需 TEE                                    │
│  └── 差分隐私: 统计输出                                        │
│       - 群体共识数据加噪后输出给供给侧                          │
│                                                               │
│  Layer 4: 身份保护 (设备指纹 + 匿名化)                         │
│  ├── 硬件指纹: 设备级唯一标识（不可逆哈希）                      │
│  ├── 匿名身份: 随机昵称 + emoji，不可搜索                       │
│  └── 零知识证明: 验证身份属性而不暴露身份                        │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 核心选型决策

| 层级 | 推荐方案 | 理由 | 备选 |
|------|---------|------|------|
| 通信加密 | **Signal Protocol** | 黄金标准、大规模验证、开源 | Matrix（去中心化需求） |
| 群聊密钥 | **MLS (RFC 9420)** | IETF 标准、前向保密、O(log n) | Megolm（简单场景） |
| 盲服务器计算 | **MiTEE + TFHE 混合** | 性能 + 安全平衡 | 纯 FHE（安全优先） |
| 匿名路由 | **待设计** | 需要专门设计 | mixnet / Tor |
| 后量子 | **PQXDH / Kyber-1024** | Signal 已支持、NIST 标准 | 持续后量子（PQ3 思路） |

### 4.3 关键技术挑战

```
1. Signal 去电话号码化
   - 问题: Signal 的 X3DH 依赖电话号码作为身份标识
   - 方案: 用设备指纹哈希替代电话号码
   - 挑战: 多设备同步、密钥恢复

2. 盲服务器的计算范围
   - 问题: 哪些计算必须在服务器完成？
   - 评估: 共鸣检测需要服务端计算，情感分析可部分端侧
   - 方案: 端侧预处理 + TEE 聚合

3. FHE 性能瓶颈
   - 问题: 复杂计算（如 NLP）在 FHE 下不现实
   - 方案: TFHE 处理简单聚合，TEE 处理复杂计算
   - 折中: 接受 TEE 的硬件信任假设

4. 元数据保护
   - 问题: 即使内容加密，通信模式仍可泄露信息
   - 方案: 批量上传、随机延迟、流量填充
   - 挑战: 用户体验 vs 隐私保护

5. 密钥管理
   - 问题: 无手机号绑定，如何恢复密钥？
   - 方案: 助记词 + 社交恢复（知己互助恢复）
   - 挑战: 用户教育、恢复安全性
```

### 4.4 分阶段实施建议

```
Phase 1 (MVP):
- Signal Protocol 基础通信加密
- 设备指纹身份绑定
- 基础 TEE 服务端处理

Phase 2 (安全增强):
- MLS 群聊加密
- Sealed Sender
- MiTEE 盲服务器聚合

Phase 3 (隐私强化):
- 匿名路由（mixnet）
- FHE 简单聚合
- 差分隐私输出

Phase 4 (前沿技术):
- 后量子加密迁移
- 零知识证明身份验证
- 端侧联邦学习
```
