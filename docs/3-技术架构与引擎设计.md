## 一、技术选型总纲

### 1.1 选型原则

| 原则 | 含义 |
|------|------|
| **隐私安全第一** | 每一层、每一个组件都必须贯彻数据安全与隐私保护 |
| **最低开销** | 优先选择资源占用低的方案，开发阶段可在单机运行 |
| **端侧优先** | 能在设备上跑的计算不下放到云端 |
| **AI 高兼容** | 对 AI 框架有极高的兼容性，支持端侧推理和云端 API |
| **独立部署** | 引擎间解耦，可单独扩容 |

### 4.4 Anchor Engine（锚点引擎）

**端口**: 8090  
**职责**: 锚点（心物）管理、质量评估、季节性重播、群体记忆重现

**核心算法要点**:
- 锚点质量评估：基于内容完整性、表达深度、情感真实性
- 季节性重播：根据时间周期触发历史锚点的重新呈现
- 锚点聚类：使用 BGE 语义 embedding + HDBSCAN 进行话题聚类
- **群体记忆重现**（TBD，由运营团队规划）：当心物随时间回归时，系统浮现历史群体记忆
  - 数据来源：Resonance Engine 的历史共鸣数据
  - 触发条件：季节性、周年、社会事件回响（触发机制待定义）
  - 展示内容：用户一年前的感想、当时共鸣人数、群体对话题理解的演变
  - 实现方式：待运营团队定义触发机制后，由 Anchor Engine 实现

**关键决策**: 语义 embedding (BGE) 是必须的，不是可选的。TF-IDF 对中文情感短文本完全无效（实验验证 ARI=0），整个锚点聚类依赖语义向量。

**gRPC 接口定义**:

### 4.5 Resonance Engine（共鸣引擎）

**端口**: 8091  
**职责**: 共鸣值计算、关系深度评估

**核心算法要点**:
- 共鸣值公式: `resonance = relevance × novelty`
- relevance: BGE 语义相似度（> 0.3 为有效共鸣）
- novelty: 表达增量，区分"复述"和"新增感悟"
- 关系深度: 相对共鸣强度，非绝对值

**五态反应推断算法**:

用户表达后，系统自动推断反应类型（用户不选择，系统后台分类）：

| 反应类型 | 推断依据 | 权重 |
|---------|---------|------|
| **共鸣** | 表达与心物的情感方向一致 + 包含个人经历或真实细节 + BGE 语义相似度 > 0.3 | 强正向 |
| **无感** | 表达简短（< 20 字）且无情感倾向词 + BGE 语义相似度 0.1-0.3 | 弱信号 |
| **反对** | 表达明确不认同（含否定词）但包含理由 + BGE 语义相似度 > 0.2 | 强负向（也是深度参与） |
| **未体验** | 表达内容与心物无关（BGE 语义相似度 < 0.1）或缺乏真实细节 | 真实性信号 |
| **有害** | 用户主动标记（必须写理由，有成本） + AI 初步确认 | 治理信号 |

**情绪词细分（共鸣反应的子分类）**:

| 情绪词 | 推断依据 |
|--------|---------|
| 同感 | 表达情感方向与心物一致，无新视角 |
| 触发 | 表达中包含"想起""回忆""那年"等个人经历关键词 |
| 启发 | 表达中包含"原来""第一次""没想到"等新视角词 |
| 震撼 | 表达简短（< 10 字）但情感强度高（BGE 向量模长大） |

**gRPC 接口定义**:

```protobuf
service ResonanceService {
  rpc CalculateResonance(CalculateRequest) returns (CalculateResponse);
  rpc GetRelationshipDepth(GetDepthRequest) returns (GetDepthResponse);
  rpc BatchResonance(BatchResonanceRequest) returns (BatchResonanceResponse);
}

message CalculateRequest {
  string anchor_id = 1;      // 心物 ID
  string user_id = 2;        // 用户匿名 ID
  string opinion_text = 3;   // 用户表达内容
}

message CalculateResponse {
  ResonanceType type = 1;    // 推断的反应类型
  EmotionWord emotion = 2;   // 情绪词（仅共鸣类型时有值）
  float relevance = 3;       // 语义相关性 (0-1)
  float novelty = 4;         // 表达增量 (0-1)
  float resonance_score = 5; // 共鸣值 = relevance × novelty
}

enum ResonanceType {
  RESONANCE = 0;   // 共鸣
  NEUTRAL = 1;     // 无感
  OPPOSE = 2;      // 反对
  UNEXPERIENCED = 3; // 未体验
  HARMFUL = 4;     // 有害
}

enum EmotionWord {
  EMPATHY = 0;     // 同感
  TRIGGER = 1;     // 触发
  INSPIRE = 2;     // 启发
  SHOCK = 3;       // 震撼
}
```

### 4.6 Governance Engine（治理引擎）

**端口**: 8092
**职责**: 内容治理、异常检测、信用评估、未体验标记处理

**采用端侧+服务端混合治理架构**：

**端侧治理（设备端完成）**：
- 敏感词检测：本地维护敏感词库，原始内容不上服务器
- 情绪分类：端侧模型判断情绪方向，上传分类结果
- 内容指纹：提取内容的抽象特征向量，用于服务端的模式匹配
- 初步风险评估：端侧对"有害"标记内容做初步分析，上传分析结果而非原始内容

**服务端治理（基于抽象特征）**：
- 规则层: 基于抽象特征的关键词/哈希匹配（快速过滤）
- 语义层: 基于内容指纹的模式匹配（深度检测）
- 信用评估: 基于用户行为模式的动态信用分
- 群体行为监测: 统计异常检测，区分真实事件与人为操纵

**关键约束**：服务端不持有可读的原始表达内容，治理决策基于抽象特征和元数据。

**未体验标记机制**:

用户可以标记某条表达为"未体验"，表示认为表达者没有真正体验过心物所描述的事物。

| 规则 | 说明 |
|------|------|
| 有成本 | 必须写理由，不能只点按钮（最低 20 字） |
| 不等于有害 | "未体验"是对真实性的判断，不是攻击 |
| 影响权重 | 被大量标记为"未体验"的内容，其"共鸣"权重降低（不删除） |
| 可审计 | 系统记录标记者实名身份，恶意标记可追责 |
| 阈值触发 | 当"未体验"标记占比 > 30% 时，触发降权 |

**标记者信用体系**:

```python
class MarkerCreditSystem:
    """标记者信用评估系统
    
    核心理念：标记是社区自治的重要机制，
    但需要防止滥用。信用体系让准确的标记者权重更高。
    """
    
    def calculate_credit_score(self, marker_id: str) -> float:
        """计算标记者的信用分
        
        信用分基于历史准确率：
        - 标记被复核为正确 → 信用上升
        - 标记被复核为无害 → 信用下降
        - 多次恶意标记 → 限制标记权限
        """
        history = self.get_marker_history(marker_id)
        
        # 1. 计算历史准确率
        total_markers = len(history)
        correct_markers = sum(1 for m in history if m.verified_correct)
        accuracy_rate = correct_markers / total_markers if total_markers > 0 else 0.5
        
        # 2. 计算信用分（0-1）
        # 新用户默认 0.5，根据准确率调整
        base_score = 0.5
        accuracy_bonus = (accuracy_rate - 0.5) * 0.4  # 准确率 100% → +0.2，0% → -0.2
        
        # 3. 惩罚机制
        # 近期恶意标记 → 额外惩罚
        recent_malicious = sum(1 for m in history[-10:] if m.is_malicious)
        malicious_penalty = recent_malicious * 0.1
        
        credit_score = base_score + accuracy_bonus - malicious_penalty
        return max(0.0, min(1.0, credit_score))
    
    def get_marker_weight(self, marker_id: str) -> float:
        """获取标记者的权重（用于标记计算）"""
        credit_score = self.calculate_credit_score(marker_id)
        
        # 信用分 → 权重映射
        # 0.0 → 0.1（几乎无权重）
        # 0.5 → 1.0（正常权重）
        # 1.0 → 2.0（高权重）
        return 0.1 + credit_score * 1.9
    
    def check_permission(self, marker_id: str) -> bool:
        """检查是否允许标记"""
        credit_score = self.calculate_credit_score(marker_id)
        
        # 信用分过低 → 限制标记权限
        if credit_score < 0.2:
            return False
        
        # 近期恶意标记过多 → 限制权限
        history = self.get_marker_history(marker_id)
        recent_malicious = sum(1 for m in history[-20:] if m.is_malicious)
        if recent_malicious >= 3:
            return False
        
        return True
```

**分级响应机制**:

| 阶段 | 触发条件 | 系统动作 |
|------|---------|---------|
| 观察 | 少量有害标记 | 不做任何处理，记录 |
| 降权 | 有害标记达到阈值 + AI 初步确认 | 降低可见度，但不屏蔽 |
| 暂停 | 有害标记继续增加 + AI 高置信度 | 暂停传播，进入复核 |
| 移除 | 复核确认有害 | 移除，通知标记者结果 |
| 反转 | 复核确认无害 | 恢复，消耗标记者在"降权"阶段的信用 |

### 4.7 User Engine（用户引擎）

**端口**: 8093  
**职责**: 信任等级管理、匿名身份维护、知己关系管理

**核心算法要点**:
- 信任等级: 基于设备指纹 + 行为模式的渐进式信任
- 匿名身份: 随机昵称 + 随机头像，无可关联信息
- 知己关系: 通过持续共鸣自然涌现，非主动添加

**信任递进阶梯（L0-L3 实现）**:

| 等级 | 名称 | 触发条件 | 体验增强 |
|------|------|---------|---------|
| L0 | 浏览心物 | 注册完成 | 看到内容，可以留下反应 |
| L1 | 痕迹可见 | 首次共鸣 | 看到他人的匿名感受，体验感受碰撞 |
| L2 | 感受回应 | ≥3 次共鸣 + ≥1 个心物 | 对他人感受链条目产生新感受，对方可能看到（异步） |
| L3 | 回达增强 | ≥10 次共鸣 + ≥3 个心物 + 双向共鸣 | 回应时可选"确保对方看到"（仍异步，但有送达感） |

**阈值计算是双向的**——必须双方的共鸣关系分都达到阈值。系统不会告诉用户"你达到了 Level X"——体验在后台静默增强，用户在自然体验中偶然发现。

**同时在场信号**：当两人恰好同时在同一心物下表达时，系统将此作为共鸣关系的加权信号，但不提供实时对话能力。感受链始终是异步的。

**知己显现条件**（与 Flutter 方案一致）:
- 关系深度光谱（0-100）达到阈值
- 双向条件：双方的共鸣关系分都达到阈值后，系统提示"有个人总是跟你有同样的感受"
- 用户永远看不到具体数字，体验在后台静默增强

## 五、关系深度算法

### 5.1 核心原则

1. **用相对值，不用绝对值** — 每个人有自己的互动基线
2. **关系深度对用户不可见** — 用户永远看不到数字
3. **个性化基线** — 尊重每个人的互动节奏
4. **个性化衰减** — 关系分随时间衰减，衰减速率基于两人互动节奏
5. **跨时空共鸣** — 心物是永恒的，不同时间对同一心物的共鸣不被衰减惩罚
6. **容量限制** — 前 N% 关系获得显著曝光

### 5.2 算法实现

```python
class RelationshipDepthCalculator:
    """关系深度计算器
    
    核心理念：关系深度是光谱，不是阶段。
    用相对值衡量两个人之间的共鸣强度，
    而不是用绝对的互动次数。
    """
    
    def calculate_relative_strength(self, resonance_count: int, 
                                     time_window: timedelta,
                                     user_a_baseline: UserBaseline,
                                     user_b_baseline: UserBaseline) -> float:
        """计算相对共鸣强度
        
        Args:
            resonance_count: 时间窗口内的共鸣次数
            time_window: 时间窗口
            user_a_baseline: 用户 A 的个性化基线
            user_b_baseline: 用户 B 的个性化基线
            
        Returns:
            相对共鸣强度（>1 表示高于预期，<1 表示低于预期）
        """
        expected_a = user_a_baseline.avg_resonance_rate * time_window.days
        expected_b = user_b_baseline.avg_resonance_rate * time_window.days
        expected = expected_a * expected_b
        return resonance_count / expected if expected > 0 else 0.0
    
    def calculate_with_decay(self, current_depth: float,
                              time_gap: timedelta,
                              user_a_baseline: UserBaseline,
                              user_b_baseline: UserBaseline) -> float:
        """个性化衰减函数

        衰减基于两人的互动节奏，不是全局统一速率。
        活跃用户衰减更快（更频繁建立新连接，老关系自然让位），
        低频用户衰减更慢（每次共鸣更珍贵）。

        Args:
            current_depth: 当前关系深度
            time_gap: 距离上次互动的时间间隔
            user_a_baseline: 用户 A 的互动基线
            user_b_baseline: 用户 B 的互动基线

        Returns:
            衰减后的关系深度
        """
        # 取两人中更活跃的作为衰减基准
        avg_interval = min(user_a_baseline.avg_interval,
                           user_b_baseline.avg_interval)

        # 1个周期内不衰减（grace period）
        periods = time_gap.days / avg_interval
        if periods <= 1.0:
            return current_depth

        # 半衰期：活跃用户~5周期，低频用户~20周期
        half_life_periods = max(5, min(20, 10 * (avg_interval / 7)))

        decay_factor = 0.5 ** ((periods - 1) / half_life_periods)
        return current_depth * decay_factor

    def calculate_cross_time_resonance(self, user_a_embedding: list[float],
                                         user_b_embedding: list[float],
                                         base_weight: float) -> float:
        """跨时空共鸣加权

        Standby 不是热点式平台，心物是永恒的。
        两人在不同时间对同一心物的共鸣是真实共鸣，不被衰减惩罚。

        Args:
            user_a_embedding: 用户 A 的感受向量
            user_b_embedding: 用户 B 的感受向量
            base_weight: 基础共鸣值

        Returns:
            跨时空共鸣值（加权系数 >= 1.0）
        """
        similarity = cosine_similarity(user_a_embedding, user_b_embedding)
        if similarity > 0.3:  # 阈值
            return base_weight * 1.0  # 跨时空加权系数 >= 1.0
        return 0.0
    
    def detect_soulmate(self, user_a_id: str, user_b_id: str,
                         resonance_history: list[ResonanceEvent]) -> bool:
        """检测知己关系
        
        当两个人在多个心物上反复共鸣，
        系统会自动提示「有个人总是跟你有同样的感受」。
        双方都选择「想认识这个人」后，可以互相看到设定昵称和头像。
        
        Args:
            user_a_id: 用户 A 的匿名 ID
            user_b_id: 用户 B 的匿名 ID
            resonance_history: 共鸣历史
            
        Returns:
            是否达到知己阈值
        """
        # 计算跨心物的共鸣分布
        anchor_count = len(set(r.anchor_id for r in resonance_history))
        total_resonances = len(resonance_history)
        
        # 需要在多个不同心物上都有共鸣（不是只在一个话题上）
        return anchor_count >= 5 and total_resonances >= 15
```

### 5.3 性能优化：事件流实时计算

每次用户产生共鸣事件，实时更新涉及的所有配对关系分。

```
用户A 对 心物X 产生共鸣
    │
    ↓
① 写入共鸣事件（O(1)）
    │
    ↓
② 查询心物X的其他共鸣者 {B1, B2, ...Bn}
   （索引：seedstone_id → [user_ids]，O(1)）
    │
    ↓
③ 对每个 Bi，计算增量共鸣值（O(n)）
   delta = f(A的反应, Bi的反应, 话题相关性, 历史关系分)
    │
    ↓
④ 更新关系分缓存（O(n)）
   new_score = old_score × decay_factor(A,Bi,time_gap) + delta
    │
    ↓
⑤ 如果 new_score 触发知己阈值 → 进入知己检测流程
```

**单事件复杂度**：O(R_x)，R_x = 心物X的共鸣者数量

**爆款限流**：当 R_x > 1000 时，只实时更新 A 的"活跃知己候选"（前N%关系），其余配对延迟到每日批量任务处理。

## 七、五层安全体系

### 7.1 安全原则

1. **端侧优先**: 敏感计算在设备上完成
2. **数据最小化**: 只收集必要的数据
3. **用户控制**: 用户可以查看和关闭任何感知
4. **透明度**: 系统行为可审计
5. **架构安全**: 通过架构设计保证物理隔离，不依赖平台善意

### 7.2 五层安全体系

#### 第一层：硬件身份验证

- 设备级硬件 ID 绑定，一人一号
- 硬件 ID 经不可逆变换后作为身份凭证，平台不持有原始硬件标识
- 攻击成本从「写脚本批量注册」变成「购买大量物理设备」，数量级提升

#### 第二层：端到端通信

- 完全切断通过互联网端口访问中心服务器的可能
- 服务器与用户设备仅通过端到端加密通道通信
- 外部爬虫、API 滥用、中间人攻击在架构上不可行

#### 第三层：盲服务器处理（混合治理架构）

- 用户原始表达不上服务器，仅在端侧完成初步分析后上传抽象特征
- 端侧分析：敏感词检测、情绪分类、内容指纹提取——原始内容留在设备上
- 服务端分析：基于抽象特征的聚合分析（模式检测、异常检测、群体行为分析）
- 群体共识的聚合在特征层面完成，服务器不持有可读的原始表达
- 即使服务器被入侵、被扣押、被内部人员接触，泄露的只有抽象特征，无法还原原始内容

#### 第四层：完全匿名

- 用户之间完全匿名，无用户名、无头像、无可关联身份的任何信息
- 表达内容不可追溯到任何个体

#### 第五层：群体行为监测（防水军）

- 在无搜索、无话题、无趋势的环境下，真实群体表达应呈现渐进、平稳、无突变的分布
- 突变型动向（突然高峰、突然集中）几乎必然是外部操纵，自动过滤不展示
- 真实世界事件引发的自然突变与人为操纵的区分：真实事件影响多维度表达，操纵通常集中在单一维度

### 7.3 五层防御的协同效应

```
硬件身份 → 一人一号，攻击成本极高
    ↓
端到端通信 → 外部完全隔绝
    ↓
盲服务器 → 端侧分析，服务端只处理抽象特征
    ↓
完全匿名 → 用户之间无从知晓彼此
    ↓
群体监测 → 漏网操纵行为被统计过滤
    ↓
没有任何单一实体能同时看到「谁说了什么」
```

## 八、技术选型依据与验证结论

本节整合了技术验证报告的核心结论，为关键技术选型提供实验依据。

### 8.1 语义编码器选型：BGE 是必须的

**验证背景**: 评估 TF-IDF 能否替代语义 embedding 用于中文情感短文本的聚类和共鸣计算。

#### 实验结论：TF-IDF 完全失败

| 方案 | ARI | NMI | 结论 |
|------|-----|-----|------|
| HDBSCAN + TF-IDF | 0.0000 | 0.0000 | 所有点被判为噪音，完全失败 |
| K-Means(K=6) + TF-IDF | -0.0112 | 0.2287 | 低于随机，各簇混杂严重 |
| HDBSCAN + BGE (min_topic_size=4) | **0.3090** | **0.5449** | 显著改善，话题结构可识别 |

**根本原因**: 中文情感短文本在语义上相关（都在谈"孤独"），但在词汇上几乎没有重叠。TF-IDF 基于词频，无法捕捉语义关系。同话题内 TF-IDF 相似度仅 0.06-0.09，跨话题 0.04-0.08，几乎无差异。

#### BGE 编码器性能基准

| 模型 | 维度 | 单条延迟 | 批量延迟 (37条) | 每条 |
|------|------|---------|----------------|------|
| bge-base-zh-v1.5 | 768 | 572ms | 1261ms | 34ms |
| bge-small-zh-v1.5 | 512 | 203ms | 379ms | 10ms |

*注: CPU 环境测量，无 GPU 加速*

**扩展性估算**:
- 云端批量编码 1000 条观点 (bge-base): ~34 秒
- 端侧单条编码 (bge-small): ~200ms（首次加载后）

**选型决策**: 
- 云端使用 bge-base-zh-v1.5 (768维)，精度优先
- 端侧使用 bge-small-zh-v1.5 (512维)，速度优先
- 双模型分工明确，满足不同场景需求

### 8.2 聚类算法选型：HDBSCAN 是正确选择

**验证结论**: HDBSCAN 在语义 embedding 输入下能有效识别话题结构。

**最优参数** (小数据集验证):
- min_topic_size = 4
- ARI = 0.309, NMI = 0.545

**聚类分布** (37 条数据):
- 簇 0 (13条): 迷茫 + 阅读 混合
- 簇 1 (12条): 城市 + 孤独 + 关系 混合  
- 簇 2 (7条): 音乐高度集中（纯度 **86%**）

**注意事项**:
- ARI 0.309 低于目标 0.6，但显著优于 TF-IDF (0.0)
- 小数据集 (37条) 下 HDBSCAN 表现不稳定，需大规模数据复验
- 部分话题边界模糊，6 个人工标签可能过于细粒度
- 聚类本身不应作为唯一的分组手段——应结合标签系统和 LLM 判断

### 8.3 Novelty 评分验证：公式有效

**验证背景**: 评估 `resonance = relevance × novelty` 公式能否区分"复述"和"增量感悟"。

#### BGE 下的 Novelty 评分结果

| 观点类型 | relevance | novelty | 验证 |
|---------|-----------|---------|------|
| 复述锚点 | 0.8101 | 0.4329 | ✅ 低增量（高相似） |
| 相似经历 | 0.7489 | 0.4605 | ✅ 中增量 |
| 全新角度 | 0.6036 | 0.5279 | ✅ 高增量（视角独特） |
| 增量感悟 | 0.6133 | 0.5439 | ✅ 高增量 |
| 不相关 | 0.2770 | 0.0000 | ✅ 正确排除 |

**关键发现**: 
- BGE 能正确区分 relevance（全部 > 0.3 除了不相关）
- novelty 能在 relevance 相近的情况下区分"复述"和"增量"
- 对比 TF-IDF：所有 relevance < 0.3，novelty 无法生效

**结论**: `relevance × novelty` 公式在语义 embedding 下有效，共鸣值公式可行。

| 验证项 | 结论 | 状态 |
|--------|------|------|

| HDBSCAN 聚类可行性 | ARI=0.309 (小数据集)，需大规模数据复验 | ⚠️ 部分验证 |
| Novelty 评分逻辑 | 能区分复述/增量/不相关 | ✅ 确认 |
| 编码器性能 | 云端批量可行，端侧可接受 | ✅ 确认 |
| bge-base vs bge-small | base 精度更高，small 更快 | ✅ 分工明确 |
